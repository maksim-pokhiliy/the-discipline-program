## Summary

The SchemaRow body editor begins — the schema body stops being empty. A coach opens a schema, taps "Add row", picks a row kind from a menu of 8, and (for `STANDALONE_LOAD`) fills a load form; the row renders in the schema body as a card with a human-readable load summary, drag-reorder / edit / delete mirroring the schema cards. Built:

- **`LoadEditor`** — a controlled sub-editor over 5 load kinds (`absolute` / `percentage` / `bodyweight` / `without_weight` / `unspecified`), `switch (value.kind)` dispatch, each kind an own-file sub-component typed at its `Extract<Load, { kind: K }>`. Reusable — Step 9.3 EXERCISE consumes it for the row-level `load`.
- **`WeightEditor`** — a controlled sub-editor over 8 weight variants, `switch (value.variant)`, each variant an own-file sub-component at its `Extract<Weight, …>`. `split_tier` carries a sub-array editor with a UI `.min(2)` floor; `with_asymmetric_arm` a toggled optional `passiveExtraWeight`.
- **`PercentageReferenceEditor`** — 2 scopes (`self` / `movement_family`); `other_exercise` deferred to Step 9.3 (D-9.1-7), the type derived via `Extract<…>` so 9.3 widens additively.
- **`LoadSummary`** — a `switch`-based formatter (`load.kind` + nested `weight.variant`) → a readable `<Chip>`.
- **`StandaloneLoadRowForm`** — a self-contained `*RowForm` (owns `useForm` + `zodResolver` + `FormModal` + `useCreateSchemaRow`/`useUpdateSchemaRow`); a static "Applies to all preceding rows" caption in place of a control for the single-value `scope` (D-9.1-3).
- **Row-kind dispatch infra** — `ROW_KIND_FORM_REGISTRY` (1 entry — `STANDALONE_LOAD`), `RowEditorModal` (thin dispatcher), `AddRowButton` (an MUI `Menu` of the 8 coach-facing rowKinds, an unimplemented pick = no-op).
- **`SchemaRowList` / `SchemaRowCard`** — the body rendering: dnd reorder (optimistic `arrayMove` + `onError` rollback), a drag-handle card with `LoadSummary` + an Edit/Delete menu. `SchemaCard` modified to embed `SchemaRowList`; an empty body shows the `AddRowButton` only, no placeholder (D-9.1-10).

## Open questions resolved

### D-9.1-4 (load-bearing) — `switch`-dispatch implemented exactly, zero escalation

The `LoadEditor` / `WeightEditor` discriminated dispatch — `switch (value.kind)` / `switch (value.variant)`, each `case` to an own-file `Extract<…>`-typed sub-component, **not** a `Record<Kind, FC>` — was specced in the thesis with the full rationale upfront (the flavour-(i) `[[planner-lint-impact-trace]]` lesson from the 8.4 prompt error, where a `Record` over heterogeneous forms erased the per-variant generic). The executor implemented it as specced; the type held; **no Design-gate escalation** — the contrast with Step 8.4, where the prompt's `SchemaEditorModal`-owns-`useForm` shape was not type-safe and approach (A) had to be ratified mid-pipeline. The 9.1 thesis applied the 8.4 lesson proactively (the type was simulated before locking the spec) and the step ran clean. Review + QA both verified the dispatch types cleanly with zero `as` / `!` / dead-branch re-narrow.

### DD-1..5 — executor design decisions (all within ratified intent, no escalation)

- **DD-2 / R4** — `standaloneLoadRowFormSchema` re-issues the `percentage.rangeMax > value` constraint with `path: ["load", "rangeMax"]` (the `RestSpecFields` path-bearing-`superRefine` precedent) so the error lands on the field. The contract `loadSchema` is untouched (D-9.1-11). A consequence — both refinements fire (the form's path-bearing one + the contract's root-pathed one) → a buried, never-rendered duplicate root error on `errors.load` (QA-304, INFO — harmless).
- **DD-3** — the row-kind picker is an MUI `Menu` (8 flat items), not a `BaseModal` — `ArchetypePicker`'s `BaseModal` is justified by 34 grouped async-fetched archetypes; the 8 static rowKinds do not warrant it.
- **DD-4** — the form schema is inline in `standalone-load-row-form.tsx`; `buildDefaultWeight` / `buildDefaultLoad` live in a shared `weight-load-defaults.ts` (pure, multi-consumer — the kind/variant switch + the form defaults).
- **DD-5** — the `LoadSummary` formatter carries a defensive `default:` arm per `switch`; the `LoadEditor` / `WeightEditor` dispatch switches carry none (exhaustive over a closed union). A deliberate asymmetry — a formatter may receive DB-sourced data, a dispatcher works over form state.
