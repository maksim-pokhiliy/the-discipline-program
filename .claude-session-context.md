### 2. Architectural decision: Admin vs Platform boundaries

- **Admin** = Business panel + Marketing CMS. Manages: blog, pages, reviews, products, contacts, user management, billing overview, exercise library (reference data). Does NOT manage training plans, workouts, logs.
- **Platform** = Coach + Athlete product experience (PWA, mobile-first). Coach creates/manages training plans, views athlete progress. Athlete views workouts, logs execution, manages subscription.
- **Principle:** Training plan is a live product, not a static CMS record. Coach and athlete work on the same content in one app with role-based interfaces.
- Committed in `docs/app-role-boundaries` branch but NOT pushed yet.

- **Sidebar** in `packages/ui` (reusable by Platform later)

## User's Working Principles (for reference)

- **Quality > Speed.** No deadlines, clean solutions preferred over fast ones.
- **Strict layer order:** DB Schema → Contracts → API Server → Client UI.
- **No any, no ts-ignore, no mock data, no temporary solutions.**
- **Named exports, arrow functions, functional components, kebab-case files.**
- **Modules pattern:** each nav item = one module.
- **Page pattern:** server component fetches data → passes to client view component.
- **Atomic components, MUI Box as base, types separated from props.**
