# 0040. Derive parallelism from structure + atomic parallel materialization (continues 0038/0039; partially supersedes 0037 and 0039 §B)

- **Status:** Superseded by ADR-0041 (the session-primitive model core — derived parallelism is replaced by an explicit, persisted `SchemaGroup` entity; `isStructurallyParallel`, the arrangement axis, `parentSchemaId` recursion, and `POST …/schemas/parallel` are all deleted). Originally: Accepted (continued the ADR-0038/0039 inert-surface drain; partially superseded ADR-0037 — `parallel` left the stored arrangement-axis vocabulary and became a derived label; partially superseded ADR-0039 §B — the toggle-based parallel authoring path was replaced by structure)
- **Date:** 2026-06-10
- **Deciders:** Maksim (owner), Claude (co-owner)
- **Tags:** `lms`, `plan-content`, `domain-model`, `api`, `yagni`

## Context

ADR-0039 made `arrangement: parallel` reachable for the first time — but through a round-trip: add ≥2 sub-schemas, go back to the parent's edit modal, set arrangement = `parallel`, toggle each child in as a track. The `compose-authoring-ux` initiative exists to kill exactly that round-trip. Its step 1 (PR #258) shipped the single-flow authoring UI (Ladder stepper → "+ another ladder") and — per the initiative-ratified D-TRACKS-DERIVED — persisted a parallel STRUCTURALLY: a parent with `composition: {}` plus N container-ladder children, with NO stored `arrangement.parallel.tracks`.

That left the stored contract carrying a parallel arm the forward path no longer writes. Three concrete problems:

1. **Stored `tracks` was a duplicated tree fact.** For every pre-step-1 parallel, `arrangement.parallel.tracks` was a verified 1:1 mirror of the parent's direct children (all 4 seed parallels + the API write guard, which forced `tracks ⊆ direct children`, min 2, distinct). Duplicated facts drift; three guard layers — the `superRefine` distinct-tracks check, the `assertArrangementRefsInScope` parallel arm, the seed two-phase back-patch — existed solely to police the duplication.
2. **The card lied to the coach.** A step-1-created parallel rendered as a plain container with two stacked ladders — `deriveCompositionLabel({})` = `flat` — because the label had no structure in scope. The coach-visible acceptance signal of this step is that "parallel" tag returning.
3. **Creation was not atomic** (initiative carry-forward MATERIALIZE-ATOMICITY). The step-1 sequencer fired 1 + N independent POSTs with no rollback: a mid-sequence failure left a partial parallel, and a retry duplicated the parent — each POST carried its own idempotency key, and client-side N-request sequences cannot be made atomic.

Additionally, the write-guard projector inherited QA-106 from `plan-editor-compose`: `buildSchemaWithBody` hard-coded `subSchemas: []` at depth 2, while real seed data (block-010, rounds-over-parallel ladders) is depth-3 — write guards validated an amputated tree.

Composition is inert (ADR-0038/0039): no executor reads `repetition`/`arrangement`/`interleaveOrder`; the only live consumers are the display label and summary strings, so the model is free to reshape. If not reshaped, the contract permanently carries two representations of parallelism (stored arm for old data, structure for new) and every future consumer must handle both.

## Decision

Parallelism is derived from the tree, never stored. Five coordinated changes landed bridge-free on one branch (no users, non-prod Neon, solo dev):

- **Structural predicate.** `arrangement.parallel` and `parallelTrackSchema` leave the contract; the arrangement union is `ordered | superset`. A schema IS parallel iff it has **≥2 container children and neither `repetition` nor `arrangement`** — `isStructurallyParallel(composition, { containerChildCount })` in `@repo/contracts` (`composition-label.ts`), the ONE shared implementation consulted by the server tree builders, the schema card, and the edit-modal draft preview. Rows (including `INNER_LADDER_MARKER`) do not count as children; an explicit `ordered`/`superset` suppresses the derivation. The predicate counts **container children, not ladder children** — wider than the D-TRACKS-DERIVED one-liner — so block-009's alternating plain-container sets stay parallel, and the no-repetition qualifier excludes EMOM slot parents; the widening was ratified by the owner at Gate A with block-009 as the forcing instance (DR-S2-1).
- **`interleaveOrder` re-homed.** It becomes an optional `compositionSchema` ROOT field (still inside the `Json` blob — no Prisma change); absent ⇒ display default `round_by_round` (`DEFAULT_INTERLEAVE_ORDER`). No tree invariant ties it to structure: a value stranded by a track deletion is display-inert rather than 400-poisoning subsequent unrelated writes (DR-S2-2).
- **Atomic materialization.** New `POST /api/platform/training-plans/[planId]/schemas/parallel` takes `{ blockId, parentSchemaId?, header?, tracks: [{ header?, steps }] (min 2) }`; the server assembles all compositions itself (only ladder tracks are materializable — D-SCOPE enforced at the transport), creates parent + tracks in ONE Serializable transaction, write-guards the resulting subtree at full depth, and returns it (`SchemaWithBody`, 201). The route factory's default-on idempotency (ADR-0036) puts ONE key on the WHOLE tree — the duplicate-parent-on-retry failure mode dies for same-key replays as a side effect; the residual window (QA-304: the client mints a fresh key per request, so a manual resubmit after a committed-but-lost response can create a second complete tree — whole, visible, deletable, never partial) is accepted. The step-1 client sequencer collapses to a single request; the create-flow UX is frozen (DR-S2-3).
- **Full-depth write guards — QA-106 closed.** All three production write-guard sites (`schema/assertions.ts`, `schema-row/admin.ts` create + update) fetch the block's schemas FLAT and project through the new `buildSchemaSubtree` (shares `buildSchemaForest`'s recursion, unbounded depth). The depth-capped `buildSchemaWithBody` is **deleted**, not fixed in place, so the cap cannot be re-adopted by a future caller. Both tree builders recompute `Schema.label` structurally after assembling children, so server labels are honest wherever children are in scope (DR-S2-7, DR-S2-4).
- **No legacy fallback.** A stored `arrangement.parallel` blob is out of contract: the strict schema fails the parse loud (500 on read, 400 on any write that re-submits it). No tolerant-reader arm, no migration shim — the ADR-0038/0039 precedent for drained fields. The seed's 4 parallel parents reshape to `{}`; the coverage gate moves to structural tallies; the remedy for stale data is `pnpm db:reset && pnpm db:seed` (DR-S2-9).

## Consequences

- **One representation of parallelism across all four projections.** Coach SETS tracks by building sub-schemas (step-1 flow); RENDER derives the tag from the same structure the cards already stack; no executor and no analytics consumer exist (inert). The dangling-track-ref bug class and the three guard layers that policed the duplication are deleted.
- **BACKLOG-ROUNDS will collide with the predicate** — restated here so the future increment does not rediscover it: "N rounds OVER a parallel block" puts `repetition` on the parallel parent, which DEFEATS the no-repetition qualifier. When that authoring lands, the predicate needs an explicit signal (and the label must learn to show both kinds). Tracked as LABEL-COMBINE in `initiatives/compose-authoring-ux/deferred.md`. Relatedly: a repetition-less parent with ≥2 sub-schemas reads "parallel" even if a coach meant a plain grouping — the escape hatch is an explicit `arrangement: ordered`.
- **Bare `create`/`update`/`reorder` responses label a parallel parent `flat`** — `mapToSchema` has no children in scope there. Bounded dishonesty: nothing renders from those responses (the card renders from the week query, whose forest builder labels structurally), and the parallel-create endpoint returns the honestly-labelled subtree.
- **Marker containers are NOT structurally parallel.** `INNER_LADDER_MARKER` rows are not container children, so a hypothetical multi-marker container (the Block C four-projection fixture) renders label-less until MARKER-FATE gets an authoring flow and its own affordance. The marker row primitive itself is untouched (sacred per D-LADDER); only the stored arrangement that pointed track refs at ROW ids — a shape already un-authorable — disappears (DR-S2-5).
- **Edit-mode parallel authoring is structural.** The toggle path ADR-0039 §B built (`ParallelArrangementFields`) is deleted; making a schema parallel = adding a second sub-schema on the card. `interleaveOrder` is editable through a slim control gated by the derived label. Untouched saves of a structurally-parallel schema round-trip `{}` (or `{ interleaveOrder }`) byte-for-byte and never touch children (DR-S2-8).
- **Contract tightens.** `.strict()` rejects any stored row carrying the removed arm; stale stored-tracks rows fail loud on read — cleared by the owner's reseed (non-prod, no real data).
- **Coverage measures structure.** The Json-path parallel tallies are replaced by a `structural.parallel` cell and a structural `entity.alternatingGroup` tally, both floored at the exact seeded count of 4 (block-009/037/087/010-middle — QA-303 tightened DR-S2-6's original 1/2 floors so a silently dropped parallel cannot pass). The gated seed-coverage suite pins the same count and asserts the seed tally helper agrees with the contracts `isStructurallyParallel` verdict on every multi-child parent, so the gate re-greens on a freshly reseeded DB and cannot drift from the predicate the product renders (DR-S2-6).
- **Initiative decision logs are superseded forward, not edited.** D-TRACKS-DERIVED's "ladder track child" letter is widened by DR-S2-1 in the initiative's `decisions.md` — the same append-only mechanism by which ADR-0038/0039 reversed their predecessors.

## Alternatives considered

1. **Atomic materialization mechanism.** Extending `POST /schemas` with recursive `subSchemas` was rejected: a dual-purpose request schema complicates the general endpoint for one flow, the response shape forks (today it returns a bare `Schema`), and arbitrary nestable child compositions re-open exactly what the dedicated schema closes. A client-side saga (compensating DELETEs on mid-failure) was rejected: compensation itself can fail and leave the same partial tree, and per-request idempotency keys still duplicate parents on retry. Reusing one idempotency key across the N-request sequence does nothing — replay of request 1 cannot resume requests 2..N. The dedicated endpoint's request shape IS the domain statement ("materialize parallel ladders"); a tight schema beats a generalized recursive create whose flexibility nothing needs.
2. **Where "parallel" reappears on read.** Synthesizing `arrangement.parallel` (with derived tracks) into the read projection was rejected: the contract would keep the parallel arm to validate responses, the edit path would fold the synthetic arm back into save payloads (round-trip hazard), and the lie moves instead of dying. Server-side `Schema.label` as the SOLE mechanism was rejected: the edit modal must label unsaved drafts client-side anyway, and bare responses without children in scope would still lie. Chosen: one shared widened `deriveCompositionLabel(composition, structure?)` + structural recomputation in the tree builders.
3. **Predicate scope: ladder-children (the D-TRACKS-DERIVED letter) vs container-children.** The literal reading was rejected: it de-classifies block-009 (alternating bench/row sets — genuinely parallel in the coach sense), and it diverges from the shipped step-1 draft predicate (`collectTrackChildren ≥ 2`) — two predicates is how the next render-collapse bug happens (step 1's CRITICAL came from a reader consulting a field instead of the structural predicate). D-SCOPE constrains what the authoring flow EMITS, not what the read layer recognizes.

## Amendments (Gate B, 2026-06-10)

Ratified at the step-2 review/QA gate; appended forward per this ADR's own supersede-don't-edit mechanism.

- **`once` ≡ absence in the structural predicate.** `isStructurallyParallel` treats `repetition: { kind: "once" }` as no repetition. QA-301 forced it: the repetition control has no "unset" — its display default IS "once" — so one exploratory toggle on a parallel parent wrote `{ kind: "once" }` into the draft and the label flipped flat permanently (no UI path removes a repetition, and the instinctive recovery — delete + recreate — is the one flow that destroys tracks). `should-be-container.ts` already encoded the same once≡no-repetition-semantics equivalence.
- **Explicit `ordered` survives the edit-save fold — the suppression escape hatch is real and authorable.** The platform fold (`build-axis-composition.ts`) normalized `ordered` → absent on every save: harmless while ordered ≡ absence for every reader, meaning-bearing under this ADR — a stored-ordered multi-child parent silently flipped to "parallel" on an untouched save, and the hatch documented in Consequences was un-authorable from the UI (REV-S2-W2). Now stored-absent stays absent, stored or deliberately-selected `ordered` re-emits `{ kind: "ordered" }` byte-for-byte, and the inspector's display-only "ordered" fallback still writes nothing.
