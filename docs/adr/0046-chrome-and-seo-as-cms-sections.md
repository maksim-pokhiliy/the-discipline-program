# 0046. Site chrome, page SEO and the public offer are CMS sections

- **Status:** Proposed (direction ratified; implementation on the delivery branch, pending merge)
- **Date:** 2026-10-30
- **Deciders:** Owner (storefront-billing D-21) and planner (step 0.4b rulings)
- **Tags:** `cms`, `localization`, `seo`, `domain-model`

## Context

[ADR-0045](0045-cms-managed-localization.md) gives the CMS a locale catalog and page sections per locale, with English as the default and fallback language. Storefront-billing D-21 assigns every buyer-facing string to CMS content or an `Intl` result so the coach can maintain the translations without a deploy. The page bodies already use that model, but page SEO titles and descriptions, navigation, footer, lead-form and error-page strings still live in code. The acquiring checklist also requires a public offer with seller details and purchase terms (D-12), which has no content surface yet.

Those surfaces need the same authoring, locale and fallback rules as page bodies. A separate settings store would duplicate those rules. The coach needs English reference text to translate, while the seller's requisites and legal terms must come from the coach rather than invented defaults. Existing production content must survive unchanged.

ADR-0021 risk 5 proposed wiring the page-level `seoTitle` and `seoDesc` columns into marketing metadata. That approach has no locale dimension. This decision replaces that proposed approach with localized sections and retires the unused metadata write. Step 0.4b delivers the contracts, readers, scaffold and route handlers; the authoring forms and public rendering follow separately.

## Decision

1. **Site chrome uses a pseudo-page with no URL.** `PageSlug.SITE = "site"` is a `MarketingPage` whose four sections are `site:navigation`, `site:footer`, `site:leadForm` and `site:errors`. They hold navigation and accessible control labels, footer copy, lead-form labels and messages, and ordinary error-page copy. Navigation labels are keyed by public page slug; link order and destinations stay in code. The language-neutral `404` glyph, generated year and site name stay in code; the global error page remains English because it renders outside the providers. `PublicPageSlug` excludes `site`, and both `PAGE_SLUG_PATH_MAP` and `marketingPagePath` accept public slugs only. The CMS API serves the pseudo-page through `GET /api/public/pages/site?locale=...`; there is no `/site` marketing page.
2. **Every public CMS page has a localized `seo` section.** The seven public page slugs are `home`, `storefront`, `about`, `blog`, `contact`, `faq` and `offer`. Each page's `seo` section holds `title` and `description`, appears last in `PAGE_SECTIONS_MAP` for editor order, and is a required nullable field of its public response. The CMS model has no keywords field. The existing marketing `PAGE_SEO`, `SEO_CONFIG` and metadata generation remain in use until step 0.4f connects these sections.
3. **The public offer uses the same page model.** `PageSlug.OFFER = "offer"` has `hero`, `requisites`, `terms` and `seo`, in that order. The hero is title and subtitle; requisites are a title and labeled values; terms are a title and ordered heading/body blocks. The public reader and `GET /api/public/pages/offer?locale=...` exist in this step. The path model gives it `/offer` in English and `/{code}/offer` otherwise; the rendered page route and sitemap entry arrive in step 0.4g. The coach owns the requisites and terms. The scaffold supplies neither real seller data nor placeholder legal text, and the three content sections have no defaults.
4. **English defaults use the existing lazy admin scaffold.** `SECTION_DEFAULTS` in `@repo/contracts/cms/pages` is the single source for eleven complete English payloads: seven `seo` sections, including `offer:seo`, and four `site` sections. Opening `getPageBySlug(slug, locale)` inserts missing sections with those defaults only for `DEFAULT_LOCALE_CODE = "en"`; every other section, and every section of another locale, starts as `{}`. `createMany` with `skipDuplicates` preserves all existing rows, including a row deliberately cleared to `{}`. The page list lazily creates missing page records; opening a page editor creates its missing section rows. A deploy itself does not seed or rewrite content. Public reads never scaffold and never merge these constants into their responses. They keep ADR-0045's fallback per section: an active, parsable, non-empty own-locale row, otherwise an English row meeting the same conditions, otherwise `null`. Parsing uses the section schema's `deepPartial()`, so a partial nested item remains in its own locale's section; missing fields are not individually filled from English. Step 0.4f will reuse the same `SECTION_DEFAULTS` constant for marketing fallback; this step does not connect that fallback to the UI.
5. **Site changes invalidate the root layout; page changes invalidate a concrete pathname.** The section PATCH uses `marketingRevalidationTarget(slug, locale)`: `site` returns `{ path: "/", type: "layout" }` for every locale, while a public page returns its concrete localized path with no `type`. The marketing revalidation route checks its secret before parsing `revalidateQuerySchema`, whose `path` must start with `/` and whose `type` is `z.literal("layout").optional()`. It calls `revalidatePath(target.path, target.type)`; an absent type preserves concrete-path revalidation. This distinction matters because `revalidatePath(path, "page")` targets route-template tags: after step 0.4f adds `[locale]`, `/uk/about` carries the `/[locale]/about/page` route tag, so the typed concrete `/uk/about/page` target would miss it. The untyped call still targets the concrete `/{code}/...` pathname. In contrast, `revalidatePath("/", "layout")` targets the root layout shared by every page and locale, which is the scope a chrome edit needs.
6. **The obsolete page-metadata writer and its admin PATCH are retired.** `GET /api/admin/pages/[slug]` remains; writes go through the section PATCH. `MarketingPage.seoTitle` and `MarketingPage.seoDesc` carry Prisma `@ignore`, which hides them from the generated client while retaining the database columns and their stored values. This step ships no migration. Removing the physical columns belongs to a later contract migration under the expand/contract discipline (D-18), separately from this retirement.

## Consequences

- **Positive:** page bodies, chrome, search copy and the offer share one content model, one locale catalog and one fallback rule. English defaults give the coach reference text without overwriting authored content. The offer's search description is a default; its seller details and legal terms remain authored content. Adding the new API surfaces changes no rendered marketing page in this step.
- **Negative:** missing or cleared English sections remain `null` in the public API until content is supplied; the planned marketing fallback can display the shared English default even after a row is cleared. Partial nested items now pass the public page reader, so consumers must tolerate missing nested fields. The admin adds Site and Offer to its Pages list, but their new section forms remain absent until 0.4d; marketing chrome and metadata consumption arrive in 0.4f, and the rendered offer page in 0.4g. ADR-0045's warning about an English edit not invalidating cached translations that fall back to it still applies; this step adds no cache mechanism for that case.
- **Neutral:** a new `site:*` section with an English default reaches existing installations through the same lazy scaffold when the page is next opened. Adding a field to an already-scaffolded section would require a backfill of the default-locale rows, because `skipDuplicates` does not update them. This step implements no such backfill; this is a consequence of the current scaffold, not a rule forbidding later fields. The retained SEO columns can be dropped in a later contract migration. The marketing-pages test fixture no longer captures or restores those ignored columns; this affects test data only.

## Alternatives considered

- **A separate `SiteSettings` table.** It would give chrome a natural settings name and keep pseudo-pages out of the slug catalog. Rejected: it creates a second content model with its own per-locale storage, fallback, scaffold, locale-deletion rules and admin read/write path, duplicating the section model already delivered by ADR-0045.
- **Message files and an i18n library.** They provide established translation tooling. Rejected by D-21: the coach owns the wording and translations in the CMS; file edits would require a developer and deploy and would split content ownership.
- **Migration-seeded English defaults.** The new rows would exist immediately after deployment. Rejected: content is not schema, deployment should not insert this copy into production, and the existing lazy scaffold already creates missing content without replacing existing rows.
- **Public readers applying the defaults.** It would make cold reads non-null. Rejected: it would hide the distinction between stored content and missing translation while leaving the admin's English reference rows empty. The public API remains a read of stored sections; later marketing consumers reuse the shared constant for display fallback.
- **Revalidating every public path after a chrome edit.** It could enumerate page and locale combinations. Rejected: that requires multiple calls and locale enumeration and can miss article paths; the shared root layout already expresses the required scope.
