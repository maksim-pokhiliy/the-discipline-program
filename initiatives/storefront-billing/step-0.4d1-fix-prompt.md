1. **RF-6 — a failed refresh after a successful save tears the editor down, and the lifecycle suite certifies the opposite through a fixture that is not the production view.** `apps/admin/src/modules/pages/views/pages-edit-view/index.tsx:19` passes the query's `error` straight to `QueryWrapper`, which renders the "Failed to load data" alert before it looks at `data` (`packages/ui/src/components/query-wrapper.tsx`); after a successful PATCH, a refresh that fails unmounts every section and every unsaved edit while "Section updated successfully" fires. Fix: pass `error={data ? null : error}` so a failure with data already loaded keeps the editor (the initial load failure still shows the alert). Drive `page-save-lifecycle.test.tsx` through the real `PagesEditView` (`render(<PagesEditView slug={…} />)`; `next/navigation` is already mocked in that file) and delete `pages-query-form.fixture.tsx` — nothing else may import it (RF-18 folds in: no singular `.fixture.` file remains). Rewrite the case "releases mutation pending after a failed invalidation GET" to assert the production behaviour through the real view: after a successful PATCH and a failed refresh every section stays mounted, an unsaved edit in another section is kept, the controls unlock, the success toast fired once and no error toast fired.

2. **RF-7 — the awaited refresh inherits the production retry policy, so every section stays locked for 7 to 67 s on a failing GET.** `apps/admin/src/lib/hooks/use-pages.ts:32-34` awaits `invalidateQueries`; the production `QueryProvider` (`packages/query/src/providers/query-provider.tsx`) sets no `retry`, so the default three retries with 1 / 2 / 4 s backoff apply (measured on the real tree: about 7 s for an instant 500, 23 s for a 503, 67 s for a hanging GET), while the test client of `apps/admin/src/test/render.tsx` runs with `retry: false` and never sees it. Fix, no new mechanism: one options factory in `use-pages.ts` — `const pageDetailsQuery = (slug: string) => ({ queryKey: adminKeys.pages.bySlug(slug), queryFn: () => api.pages.getPageBySlug(slug) })` — used by `usePageDetails` (spread it, keep `enabled: !!slug`) and by the mutation's `onSuccess`, which becomes `await queryClient.fetchQuery({ ...pageDetailsQuery(slug), staleTime: 0 }).catch(() => undefined)` before the success toast. `fetchQuery` runs one attempt (query-core 5.80.2 defaults its `retry` to `false`); `staleTime: 0` forces the fetch past the provider's thirty-second staleness; the catch keeps a failed refresh away from `onError`, because the PATCH did succeed. The repo has no `queryOptions` helper precedent; keep the plain factory. Regression test owed: one lifecycle case on a QueryClient built with the production defaults (no `retry: false`; mirror the provider's options in the test, or render through the real `QueryProvider`) proving that after a successful PATCH and a failed refresh the controls unlock after exactly one refresh GET (`getPageBySlug` called twice in total) — this is the case where the old `invalidateQueries` would have retried.

3. **RF-8 — the RF-3 key is incomplete: a refresh to a non-empty document that lost an array key leaves ghost rows, and saving them is a 400.** `apps/admin/src/modules/pages/components/section-editor/section-editor-key.ts:3-4` keys the editor on emptiness only; react-hook-form 7.60 `useFieldArray` adopts arrays only, so a `values` reset to `{ title }` keeps the previous rows with blank inputs (`Requisites (2)` with labels `["", ""]`), the next save sends `items: [null, { label: "Typed" }]` and the server rejects it ("data.items.0: Expected object, received null"); the same in whyChoose, journey, credentials, faq and terms. Fix, the ruled shape: key on the sorted top-level key set — `${section.id}:${Object.keys(section.data).sort().join(",")}` — so a changed key set remounts the section and an equal key set keeps the `values` path with its preservation of unsaved edits. Update `section-editor-key.test.ts` (equal key sets in any order share a key; a dropped or added key changes it; the empty document keeps its own key). Regression test owed: a populated `offer:requisites` (two rows) refreshed to `{ title }` shows `Requisites (0)`, and after adding one row the next save body parses against `updatePageSectionBodySchema` and carries that row only. The reviewer's alternative (seeding missing array keys from the schema) is not taken.
