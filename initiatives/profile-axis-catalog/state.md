## Gotchas a resuming session must know

- **gender is NOT in the catalog as data** (D-1) — it stays a typed column. The system Gender axis holds only the axis DEFINITION (label/values/binding); the bound axis READS the column, never writes a gender value into the catalog or `profileSelections`. The bound arm is `binding="GENDER"`; a plain coach axis is `binding=null`.
- **Single-path is by construction** — `binding` is NOT in `createProfileAxisSchema`/`updateProfileAxisSchema` (not API-settable) + `@@unique([binding])` + the protected system row (CRUD `assertNotProtected` → 403). There is NO way to author a second gender differentiation. A coach-named plain "Gender" axis is `binding=null` (a manual-pick training axis) — it never reads the typed column, so it can't masquerade as gender. Label text is deliberately NOT policed.
- **The resolver branches on the snapshot's `binding`, never reads `ProfileAxis`** — `GENDER` → typed `gender` via the LOCAL `GENDER_TO_COORD` (NOT `mappers/coaching` — `api-server-lms-no-coaching`); `null` → `profileSelections[axisId]`. Zero new query (`gender` already selected). `binding` is a LOCAL `z.literal("GENDER")` in `load.ts` (lms↛coaching is a contracts dep-cruiser boundary) — agreement with the catalog enum is pinned by a test, not a shared import.
- **The system row's `values` (`["Male","Female"]`, set by the migration) MUST equal `GENDER_AXIS_VALUES`** (the resolver coord vocabulary). Pinned ungated in `load.test.ts` (REVIEW-001) + in the gated api-server suite (reads the seeded row). A coord rename now fails pre-push.
- **The migration `20260623083123_add_profile_axis_binding`** does the repo's FIRST data-INSERT (the system row, `ON CONFLICT ("binding") DO NOTHING`). Reserved id `cgender000000000000000000` (valid cuid).
