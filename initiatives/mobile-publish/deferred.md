# mobile-publish — deferred (carry-forwards / WARNINGs)

Status: `OPEN` / `SCHEDULED` / `CLOSED` / `DROPPED`.

- **MP-1 — Individual identity picker.** **CLOSED (P2b — D-16; end-to-end).** The coach links a platform enrollment → a legacy `user_id` chosen from `GET /user?userPlanId=2`; manual + coach-driven, no auto-match (D-2/D-3). P2a landed the SERVER half (D-14): the identity columns + CHECK + bijection uniques, the live athletes proxy, the `z.union` create-link variant, the channel-aware publish. **P2b shipped the coach UI (D-16):** the per-enrollment athlete picker (plan enrollment paired against the live legacy list, bijection-excluded), the link-modal "Athletes" section (`IndividualLinksSection`/`IndividualLinkRow`, link + unlink), the strip + publish-modal individual display (grouped by platform athlete name, the `Level null` path killed), and the client slice/hook/key (`useMobileAthletes` + `platformKeys.mobile.athletes()`). Residual P2b polish → MP-16; weight-baking → MP-2.
- **MP-2 — Bake resolved weights for Individual.** OPEN (P2-tail / optional). For an Individual link we know the athlete's 1RMs → can render resolved kg into the text instead of "%". General can't (shared by level). P2a stores `athleteId` so this is now a pure follow-up (an additive `renderRowLine` ctx change).
- **MP-3 — Delete-propagation.** OPEN (P3). If a coach deletes / un-publishes a day, do we DELETE the legacy row or leave it? Default lean: an explicit un-publish DELETEs; a plain platform edit never deletes.
- **MP-4 — Token-expiry UX.** OPEN (P3). Legacy JWT TTL = 1 month, no refresh endpoint → store expiry, prompt reconnect before it lapses; a publish on an expired token must fail gracefully (re-connect CTA).
- **MP-5 — `Week.startDate` = Monday assumption.** CLOSED (P1a — VERIFIED). Research confirmed `Week.startDate` is non-nullable + always a UTC-midnight Monday (triple-guaranteed); the projection uses `sessionAbsoluteDateFromParts(week.startDate, day.dayOfWeek)` (MONDAY=0…SUNDAY=6), UTC-serialized via `utils/date-param.ts`.
- **MP-6 — Training-level name drift.** MITIGATED / standing rule (P1a). `GET /trainingLevel/all` is always read live (the `training-levels` endpoint proxies it; the gated T16 asserts level Pro=id 2 read live); ids/names are never hardcoded. Keep reading live in P2 (the Individual athlete picker).
- **MP-7 — Publish-endpoints placement vs dep-cruiser.** CLOSED (P1a — D-6). Connector lives in `endpoints/coaching/mobile-publish/` reading lms read-models (Coaching→LMS allowed); the legacy client in `infrastructure/legacy-mobile/`. No new context, no new rule; `pnpm dep:check` clean.
- **MP-8 — No legacy unique constraint on (key, date).** OPEN (mitigated, P1a). Our-side `upsert` on `(linkId, scheduledDate)` is race-free; the legacy 409→PUT fallback + the overwrite-guard re-decide (D-9) converge concurrent publishes without clobbering coach-authored days. Residual: the legacy `findByTrainingLevelIdAndDate` check is non-atomic (no DB unique) → a true TOCTOU could still double-insert on the legacy side — un-closeable from our side (D-1). Documented limitation; no distributed lock in P1a.
- **MP-9 — Token encryption key rotation.** OPEN (P3). D-7 uses a single `MOBILE_PUBLISH_ENCRYPTION_KEY`; rotating it invalidates all stored tokens → every coach reconnects (acceptable for a handful of coaches). A future envelope-encryption / key-version-prefix scheme would rotate without mass reconnect.
- **MP-10 — Week-publish resilience / latency.** OPEN (P3). A week publish does up to 7×(GET+write) sequential legacy calls with no overall deadline → a slow legacy could approach the serverless function limit. Per-day failures are now isolated (`failed` action) and an idempotent re-publish recovers (already-done days → `skipped`); P3 could batch/parallelize or background the publish + add a per-call budget. (The design's contingent "MP-10 = consolidate a copied renderer" never applied — D-8 chose the true-SSOT extraction (b), so no copied renderer exists.)
- **MP-11 — Are row notes athlete-facing?** OPEN (owner decision, P1b/P2). The projection currently does NOT publish `row.notes` to the legacy free-text (matching the platform SessionCard, which hides them via `notes:[]`). If notes are meant for athletes → publish them AND display them on the platform card (re-add the notes line in `renderRowLine` + the platform `buildSummary`); if they're coach-private cues → keep them out of the legacy projection. A product call surfaced by the PR #317 review.
- **MP-12 — Disconnect (`DELETE /connections`).** OPEN (P3, blocked on a cascade-semantics decision — D-11). P1b ships unlink (`DELETE /links/[id]`) but NOT disconnect; the connect section shows "Reconnect", not "Disconnect". `MobilePublishLink.connection` AND `MobilePublishedDay.link` are both `onDelete: Cascade` (`schema.prisma:152,171`) → a naive `DELETE /connections` cascade-wipes every plan's link AND the whole publish ledger for that coach (unbounded blast radius). P3 must FIRST resolve warn-and-cascade vs restrict-if-linked, then build the affordance. Reconnect-via-POST (the `connect` upsert, MP-4) covers the monthly expiry need, so disconnect is teardown-only and non-urgent. (Distinct from MP-4, which is the token-expiry reconnect UX.)
- **MP-13 — P1b deferred polish (UX/edge follow-ups).** OPEN (non-blocking; all recoverable, NO data loss — from `.feature-dev/1782384353/qa.md`). The 2 CRITICAL publish-concurrency races were FIXED pre-merge (QA-001 close/reopen double-publish, QA-002 double-click overwrite clobber) and the D-4 reconnect erosion (QA-006); these residual items are consciously deferred:
  - **QA-004 (re-publish after Cancel).** After Cancel on the overwrite confirm, the conflict chips stay but there's no in-panel re-trigger — the coach must close the modal and re-click "Publish this week" to re-attempt the overwrite. Consider an in-panel "Overwrite conflicting days" affordance. **Owner UX call** (coach-daily-UX).
  - **QA-007 / QA-020 (live-prop desync).** `PublishWeekModal` reads the live `links` prop; if a link is unlinked mid-publish (e.g. via the manage modal in the same screen) the modal can desync / hit a 404 on a dead link. Snapshot `links` into modal state on open to freeze the target set. Rare, recoverable (404 → error group).
  - **QA-011 (dual-CTA coordination).** When a `conflict` (one level) and a `reconnect` (another level) coexist across a multi-link publish, the overwrite confirm and the reconnect CTA can both be live with no ordering guidance. Prioritize reconnect, suppress the overwrite confirm until reconnected, then re-evaluate conflicts.
  - **Residual double legacy round-trip.** Closing + reopening mid-publish can still produce a double legacy round-trip; idempotent-safe per D-9 (the per-(linkId,date) upsert + 409→PUT converge it without clobbering a coach-authored day).
- **MP-14 — `cap`→`AMRAP` correction in the SHARED formatter (athlete-facing).** OPEN (owner decision). Publish-syntax v2 (D-13) fixed `timeCap`→`AMRAP` in the mobile **projection** only (`format-legacy-schema.ts` relabels it). The same domain bug lives in the shared `@repo/contracts/lms/composition` `formatRepetitionLabel` (renders a `timeCap` repetition as `cap N’`) + its byte-dup `apps/platform/.../lib/format-composition-summary.ts`, which drive the **athlete-session view, the records-view scheme subline, and the plan-editor composition tag** — all currently mislabel an AMRAP as `cap`. Fix = add an `amrapLabel` beside `capLabel` (keep `capLabel` for the cross-cutting `composition.cap` field) in both copies + update ~5 test files (contracts `format-composition-summary.test.ts`, api-server `records-view/build-records-view.test.ts:561`, platform `format-composition-summary.test.ts` + `athlete-session-presentation.test.ts`). Deferred out of the projection-only PR because it changes athlete-facing UI and wants its own ratification; also a chance to unify the platform byte-dup with contracts (the standing tech-debt). → `design-publish-syntax.md` §9.
- **MP-15 — Individual DELETE+POST non-atomicity.** OPEN (P2-tail / P3; documented residual, from P2a Review+QA QA-01). The legacy Individual PUT is broken (D-15) → "replace" = DELETE-then-POST, which is not atomic: a crash/timeout after the DELETE before the POST leaves the athlete's day blank until an idempotent re-publish re-POSTs (and if the replaced day was an UNOWNED overwrite, the athlete's original in-app content is gone — but the coach explicitly chose `overwriteUnowned=true`). DELETE-first ordering is mandatory; the overwrite-guard (D-4) still gates unowned writes; nothing depends on a stable individual legacyRowId (the iOS app fetches by (userId,date)). No distributed lock / compensating restore in P2a — Individual isn't live yet (no picker). A P3 hardening could add a compensating restore (capture the pre-image, re-POST it on POST-failure) or a batched/transactional path. Distinct from MP-8 (legacy TOCTOU) and MP-10 (week-publish latency).
- **MP-16 — P2b deferred polish (UX/edge follow-ups).** OPEN (non-blocking; all recoverable, NO data loss / NO general-channel regression — from `.feature-dev/1782485060/{review,qa}.md`, Gate-B-ratified deferrals). The Gate-B fix set (QA-01 graceful-degrade, QA-05 empty-options hint, QA-07 loading flashes, REV-I1 empty-selection guard, QA-03 create-copy) shipped IN the P2b PR; these residual items are consciously deferred:
  - **QA-02 (new legacy surface on Denys's live modal).** Opening Manage now fires `useMobileAthletes` (a new per-open legacy round-trip) and renders an Athletes section on a General-only coach's modal. Inherent to the feature; General CRUD is unaffected and the QA-01 graceful-degrade keeps a legacy outage from blanking the modal. Owner-awareness; optionally lazy-mount the section behind a disclosure / only fetch when the coach has an individual link.
  - **QA-03 delete-copy.** The create-error copy is now channel-aware; `useDeleteMobileLink` still says "Failed to unlink training level" for an athlete unlink (the delete mutation's variables = the linkId only, no channel → a channel-aware delete copy would thread channel through the shared hook + the General call). Rare failure; deferred.
  - **QA-04 (section-wide mutation lock).** `isMutating = createLink.isPending || deleteLink.isPending` is section-wide → bulk pairing serializes (every row freezes during any one mutation). Scope the disabled state to the in-flight `athleteId` (per-row). Not the daily flow (a coach links a handful); the relaxation also slightly widens QA-06 (server bijection stays the backstop).
  - **QA-06 (double-link race).** The proactive `legacyOptions` exclusion derives from the `useMobileLinks` query; a create-then-pick-same-id before the links refetch lets a second `createLink` fire → the server NULLS-DISTINCT unique rejects it cleanly (no corruption, no silent steal — D-14). Acceptable backstop; a regression test was added. Optionally optimistic-update the links on create success.
  - **QA-09 (legacy id > 2^53).** A legacy `Long` user_id beyond `Number.MAX_SAFE_INTEGER` coerces through the contract (`z.number().int()`) + the picker `Number()` round-trip. Pre-existing P2a contract limit; dormant (legacy ids are small); carry `legacyUserId` as a string end-to-end only if that ever changes.
  - **QA-10 (resolveHeading non-exhaustive).** `resolveHeading` / the strip partition branch general-vs-not (`isGeneralMobileLink(link) ? … : individual`); type-safe on the 2-arm union today, but a future 3rd channel would be mislabeled in publish and dropped from the strip's status partition while still publishing. Branch on `isIndividualMobileLink` explicitly with a defined fallback / `assertNever` if a 3rd channel is added.
  - **QA-11 (create-request arms non-strict).** Neither `createMobileLinkSchema` arm is `.strict()` → a malformed mixed payload (`{planId, legacyLevelId, channel:"INDIVIDUAL"}`) coerces to GENERAL rather than rejecting. No UI call site produces it; harden with `.strict()` on both arms (a P2a contract change).
  - **QA-12 (empty-string display name).** A roster `name === ""` (not null) falls through `name ?? email` to the raw `athleteId` cuid in the row chip and a blank clause in the strip. Treat blank-after-trim as missing (`name?.trim() || email`). Rare; defensive.
  - **QA-13 (no error boundary around the section).** A future render throw in `IndividualLinksSection` would white-screen the whole Manage modal incl. Denys's General CRUD (they share one `Stack`). No current throw path (defensively coded); a small error boundary degrading to an inline alert would isolate General per the byte-identical spirit. Defense-in-depth follow-up.
  - **REV-I3 (reconnect-CTA triplication).** The `<Alert> + Reconnect <Button> + <ConnectMobileModal>` block + `RECONNECT_TITLE` literal now live in 3 mobile components (manage modal, publish modal, the new section) — matches the existing P1b pattern; a future `<ReconnectCallout>` in `@repo/ui` collapses all three. Standing DRY backlog.
  - **REV-I4 (`PUBLISH_DISABLED_TOOLTIP` micro-copy).** "Link a training level first" is now mildly imprecise once an individual link also enables Publish; General-visible copy, owner-deferred at Gate A (recommend "Link a training level or athlete first"). No MT-14 assertion reads it.
- **MP-17 — Unnamed row-group blank-line asymmetry.** OPEN (owner-flag; from `.feature-dev/1782551544/qa.md` QA-004). An unnamed `RowGroup` gets a blank line BEFORE its members (only when preceded by body content) but none AFTER → a following ungrouped row butts onto the group's last member, so the group's END is invisible (you can see where it STARTS, not where it ends); a named group's label likewise has no leading blank. This is the D-5 v3 "leading-blank-only" default. **Owner reviewed at Gate B (2026-06-27) and chose to KEEP the D-5 default** — no prod data exercises it (Денys's groups are all NAMED, so the named-label path always runs and the asymmetry never shows). Revisit (symmetric blanks around every group, or a leading blank before named labels too) only if an UNNAMED group ever ships; lock the chosen variant with a test then. (`design-publish-syntax.md` §v3.4 D-5.)
- **MP-18 — `count` "N rounds" suppressed when the header conveys the digit.** CLOSED (non-issue; from QA-003). `headerConveysLabel(header, label)` collapses the append when the header (lowercased) contains the label's lead token; for `count` the lead token is a bare digit, so a header containing that digit anywhere (`"Back Squat 5 sets"` + `count:5`) suppresses the `· 5 rounds` append. This is the **design-intended `headerConveysLabel` collapse** — the pre-existing heuristic that keeps `5x5 · 5 rounds` / `AMRAP · AMRAP` from doubling, now also covering `count` — NOT a bug. Where the coach DIDN'T already convey the count, RC-1 appends it (the fix); where he did, the collapse is correct. Behavior locked by test. (A stricter "require the full `N rounds` / standalone-digit token to collapse" redesign is out of this projection-only scope; flagged only.)
- **MP-19 — Headerless `once` renders a bare `once:` line.** OPEN (pre-existing, LOW; from `.feature-dev/1782551544/review.md` REV-004). A `once` schema with NO header renders `once:` as its header line — `buildStructureText`'s `header === ""` branch returns the label directly and never consults `STRUCTURE_APPEND_KINDS` (the `· once` suppression, D-2, only applies when a header IS present). This **predates v3** (the diff only added `count` to the set, affecting the header-present path); no prod data has a headerless `once` (Денys's `once` schemas carry headers). Out of this projection-only scope. If a headerless `once` ever appears and `once:` reads as noise, a follow-up maps `once → null` in `structureLabel`.
- **MP-20 — Multi-element row-group `notes`: only `notes[0]` surfaced.** CLOSED (by design; from REV-003). `rowGroupLabel` reads `group.notes?.[0]` only — a row-group with `notes:["1st round:", "ignored"]` surfaces just the first, mirroring the platform athlete view (`build-session-detail.ts` uses `notes?.[0] ?? null`). Intentional SSOT parity, not a drop bug; documented + locked by a test asserting `notes[1]` is absent.
- **MP-21 — Soft-deleted plan leaves orphaned MobilePublishLink/MobilePublishedDay + no legacy un-publish.** OPEN (owner-ratified disposition; from PR #323 review, 2026-06-27). The old hard-delete FK-cascaded a plan's mobile links + published-days away (`MobilePublishLink.plan` / `MobilePublishedDay` are `onDelete: Cascade`); the C1 soft-delete fix (PR #323) intentionally keeps them. **Ratified: keep the rows — consistent with "soft-delete = preserve history"** (publish-history is athlete/coach audit-trail, like the preserved PerformedSession chain; do NOT reproduce part of the hard-delete bug for symmetry). Verified harmless in our DB: all 3 `MobilePublishLink` readers (`links.ts:125`, `publish.ts:39`, `authz/mobile-publish-guards.ts:6`) + the `MobilePublishedDay` reader (`publish-day.ts:168`) gate through `verifyPlanOwnership` → 404 on a soft-deleted plan, and `@@unique([planId, channel, …])` keys on `planId` so re-creating a plan never collides. **Residual (NOT a PR #323 regression — hard-delete didn't un-publish either):** deleting a plan sends NO un-publish to legacy iOS, so the athlete keeps seeing the deleted plan's days on their phone. Un-publish-on-delete (a legacy DELETE in the delete flow + failure handling, likely via `ChannelProgramOps`) is initiative-scoped feature work — fold into the delete-propagation / disconnect track (relates to MP-3, MP-12).
- **MP-22 — Link ≠ publish: per-link publish status + primary-action Publish.** SCHEDULED (post-UAT W2; owner spec 2026-07-16; prod incident same day). After creating a link the strip reads "Publishes to: <athlete/level>" — present tense, reads as "already flowing"; there is no "linked but never published" state, no last-published date, and "Publish this week" looks like an option, not a mandatory step. Incident: Denys created an INDIVIDUAL link for Stas at 10:58:40 UTC, never pressed Publish, asked Stas to check the app 19 seconds later → app empty (legacy `userPlanId=2` looks for a personal program that was never sent) → half an hour of debugging + athlete back-and-forth. Verified: zero `/api/platform/mobile/publish` requests that day, zero `app_mobile_published_days` rows for the link, zero 4xx/5xx — the system behaved correctly; pure UX failure. Fix (~half a day, `/feature small`): (1) GET /links → additive per-link aggregate from `app_mobile_published_days` (`count + max(publishedAt)`); (2) `mobile-publishing-strip.tsx` / `IndividualLinkRow` → per-link status "Never published" (accented, not gray) / "Last published: 11 Jul"; (3) while a link has zero publishes, "Publish this week" renders as the PRIMARY action (not a peer of Manage); (4) fold in REV-I4 (tooltip → "Link a training level or athlete first"). Guard: the status is WEEK-scoped — "Publish this week" sends ONLY the on-screen week, so a "last published" line must not read as "the whole plan is sent"; write the copy accordingly. Registry pointer: `post-uat` PU-08 (W2).
- **MP-NORTH-STAR — Repoint iOS at the platform API.** OPEN (future initiative). Build legacy-contract-compatible endpoints in the platform, migrate the iOS baseURL + accounts, retire the Java backend. ADR-0005/0020 anticipate it. Out of THIS initiative's scope (D-1).
