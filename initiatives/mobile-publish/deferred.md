# mobile-publish — deferred (carry-forwards / WARNINGs)

Status: `OPEN` / `SCHEDULED` / `CLOSED` / `DROPPED`.

- **MP-1 — Individual identity picker.** OPEN (P2b). The coach links a platform enrollment → a legacy `user_id` chosen from `GET /user?userPlanId=2`. No automatic matching; manual + coach-driven (D-2/D-3). **P2a landed the SERVER half (D-14):** the identity columns (athleteId + legacyUserId) + CHECK + bijection uniques, the live athletes proxy (`GET /api/platform/mobile/athletes` → legacy `GET /user?userPlanId=2`), the `z.union` create-link individual variant, and the per-athlete publish (channel-aware seam). **P2b = the coach UI:** the athlete picker (sourced from the plan enrollment, paired against the live legacy athlete list), the link-modal individual mode, the strip/publish-modal individual display (grouped by athlete, not "Level null"), and the client slice/hook/key (`useMobileAthletes`).
- **MP-2 — Bake resolved weights for Individual.** OPEN (P2-tail / optional). For an Individual link we know the athlete's 1RMs → can render resolved kg into the text instead of "%". General can't (shared by level). P2a stores `athleteId` so this is now a pure follow-up (an additive `renderRowLine` ctx change).
- **MP-3 — Delete-propagation.** OPEN (P3). If a coach deletes / un-publishes a day, do we DELETE the legacy row or leave it? Default lean: an explicit un-publish DELETEs; a plain platform edit never deletes.
- **MP-4 — Token-expiry UX.** OPEN (P3). Legacy JWT TTL = 1 month, no refresh endpoint → store expiry, prompt reconnect before it lapses; a publish on an expired token must fail gracefully (re-connect CTA).
- **MP-5 — `Week.startDate` = Monday assumption.** CLOSED (P1a — VERIFIED). Research confirmed `Week.startDate` is non-nullable + always a UTC-midnight Monday (triple-guaranteed); the projection uses `sessionAbsoluteDateFromParts(week.startDate, day.dayOfWeek)` (MONDAY=0…SUNDAY=6), UTC-serialized via `utils/date-param.ts`.
- **MP-6 — Training-level name drift.** MITIGATED / standing rule (P1a). `GET /trainingLevel/all` is always read live (the `training-levels` endpoint proxies it; the gated T16 asserts level Pro=id 2 read live); ids/names are never hardcoded. Keep reading live in P2 (the Individual athlete picker).
- **MP-7 — Publish-endpoints placement vs dep-cruiser.** CLOSED (P1a — D-6). Connector lives in `endpoints/coaching/mobile-publish/` reading lms read-models (Coaching→LMS allowed); the legacy client in `infrastructure/legacy-mobile/`. No new context, no new rule; `pnpm dep:check` clean.
- **MP-8 — No legacy unique constraint on (key, date).** OPEN (mitigated, P1a). Our-side `upsert` on `(linkId, scheduledDate)` is race-free; the legacy 409→PUT fallback + the overwrite-guard re-decide (D-9) converge concurrent publishes without clobbering coach-authored days. Residual: the legacy `findByTrainingLevelIdAndDate` check is non-atomic (no DB unique) → a true TOCTOU could still double-insert on the legacy side — un-closeable from our side (D-1). Documented limitation; no distributed lock in P1a.
- **MP-9 — Token encryption key rotation.** OPEN (P3). D-7 uses a single `MOBILE_PUBLISH_ENCRYPTION_KEY`; rotating it invalidates all stored tokens → every coach reconnects (acceptable for a handful of coaches). A future envelope-encryption / key-version-prefix scheme would rotate without mass reconnect.
- **MP-10 — Week-publish resilience / latency.** OPEN (P3). A week publish does up to 7×(GET+write) sequential legacy calls with no overall deadline → a slow legacy could approach the serverless function limit. Per-day failures are now isolated (`failed` action) and an idempotent re-publish recovers (already-done days → `skipped`); P3 could batch/parallelize or background the publish + add a per-call budget. (The design's contingent "MP-10 = consolidate a copied renderer" never applied — D-8 chose the true-SSOT extraction (b), so no copied renderer exists.)
- **MP-11 — Are row notes athlete-facing?** OPEN (owner decision, P1b/P2). The projection currently does NOT publish `row.notes` to the legacy free-text (matching the platform SessionCard, which hides them via `notes:[]`). If notes are meant for athletes → publish them AND display them on the platform card (re-add the notes line in `renderRowLine` + the platform `buildSummary`); if they're coach-private cues → keep them out of the legacy projection. A product call surfaced by the PR #317 review.
- **MP-12 — Disconnect (`DELETE /connections`).** OPEN (P3, blocked on a cascade-semantics decision — D-11). P1b ships unlink (`DELETE /links/[id]`) but NOT disconnect; the connect section shows "Reconnect", not "Disconnect". `MobilePublishLink.connection` AND `MobilePublishedDay.link` are both `onDelete: Cascade` (`schema.prisma:152,171`) → a naive `DELETE /connections` cascade-wipes every plan's link AND the whole publish ledger for that coach (unbounded blast radius). P3 must FIRST resolve warn-and-cascade vs restrict-if-linked, then build the affordance. Reconnect-via-POST (the `connect` upsert, MP-4) covers the monthly expiry need, so disconnect is teardown-only and non-urgent. (Distinct from MP-4, which is the token-expiry reconnect UX.)
- **MP-13 — P1b deferred polish (UX/edge follow-ups).** OPEN (non-blocking; all recoverable, NO data loss — from `.feature-dev/1782384353/qa.md`). The 2 CRITICAL publish-concurrency races were FIXED pre-merge (QA-001 close/reopen double-publish, QA-002 double-click overwrite clobber) and the D-4 reconnect erosion (QA-006); these residual items are consciously deferred:
  - **QA-004 (re-publish after Cancel).** After Cancel on the overwrite confirm, the conflict chips stay but there's no in-panel re-trigger — the coach must close the modal and re-click "Publish this week" to re-attempt the overwrite. Consider an in-panel "Overwrite conflicting days" affordance. **Owner UX call** (coach-daily-UX).
  - **QA-007 / QA-020 (live-prop desync).** `PublishWeekModal` reads the live `links` prop; if a link is unlinked mid-publish (e.g. via the manage modal in the same screen) the modal can desync / hit a 404 on a dead link. Snapshot `links` into modal state on open to freeze the target set. Rare, recoverable (404 → error group).
  - **QA-011 (dual-CTA coordination).** When a `conflict` (one level) and a `reconnect` (another level) coexist across a multi-link publish, the overwrite confirm and the reconnect CTA can both be live with no ordering guidance. Prioritize reconnect, suppress the overwrite confirm until reconnected, then re-evaluate conflicts.
  - **Residual double legacy round-trip.** Closing + reopening mid-publish can still produce a double legacy round-trip; idempotent-safe per D-9 (the per-(linkId,date) upsert + 409→PUT converge it without clobbering a coach-authored day).
- **MP-14 — `cap`→`AMRAP` correction in the SHARED formatter (athlete-facing).** OPEN (owner decision). Publish-syntax v2 (D-13) fixed `timeCap`→`AMRAP` in the mobile **projection** only (`format-legacy-schema.ts` relabels it). The same domain bug lives in the shared `@repo/contracts/lms/composition` `formatRepetitionLabel` (renders a `timeCap` repetition as `cap N’`) + its byte-dup `apps/platform/.../lib/format-composition-summary.ts`, which drive the **athlete-session view, the records-view scheme subline, and the plan-editor composition tag** — all currently mislabel an AMRAP as `cap`. Fix = add an `amrapLabel` beside `capLabel` (keep `capLabel` for the cross-cutting `composition.cap` field) in both copies + update ~5 test files (contracts `format-composition-summary.test.ts`, api-server `records-view/build-records-view.test.ts:561`, platform `format-composition-summary.test.ts` + `athlete-session-presentation.test.ts`). Deferred out of the projection-only PR because it changes athlete-facing UI and wants its own ratification; also a chance to unify the platform byte-dup with contracts (the standing tech-debt). → `design-publish-syntax.md` §9.
- **MP-15 — Individual DELETE+POST non-atomicity.** OPEN (P2-tail / P3; documented residual, from P2a Review+QA QA-01). The legacy Individual PUT is broken (D-15) → "replace" = DELETE-then-POST, which is not atomic: a crash/timeout after the DELETE before the POST leaves the athlete's day blank until an idempotent re-publish re-POSTs (and if the replaced day was an UNOWNED overwrite, the athlete's original in-app content is gone — but the coach explicitly chose `overwriteUnowned=true`). DELETE-first ordering is mandatory; the overwrite-guard (D-4) still gates unowned writes; nothing depends on a stable individual legacyRowId (the iOS app fetches by (userId,date)). No distributed lock / compensating restore in P2a — Individual isn't live yet (no picker). A P3 hardening could add a compensating restore (capture the pre-image, re-POST it on POST-failure) or a batched/transactional path. Distinct from MP-8 (legacy TOCTOU) and MP-10 (week-publish latency).
- **MP-NORTH-STAR — Repoint iOS at the platform API.** OPEN (future initiative). Build legacy-contract-compatible endpoints in the platform, migrate the iOS baseURL + accounts, retire the Java backend. ADR-0005/0020 anticipate it. Out of THIS initiative's scope (D-1).
