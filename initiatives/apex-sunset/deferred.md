- **AS-9.** Surfaced at P1.1 while verifying RF-2 (the shim-signin-vs-web-login lockout lever): the reason RF-2 is only LATENT is that `defaultRateLimiter` (`packages/api-routes/src/rate-limit/rate-limiter-registry.ts`) checks `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN` at boot and, finding neither set in the platform Vercel project, falls back to `createNoopRateLimiter()` — every `RATE_LIMIT_TIER` check passes. So today the whole platform (web login, password-reset, the new shim signin) is unthrottled in prod. This is bigger than apex-sunset (it's the platform's standing security posture) but it makes the ratified R2 brute-force bound vacuous in prod, so it rides here until the owner decides. Wiring Upstash is now safe because RF-2's `shim-auth:` namespace stops the shim from sharing the web login's bucket.
- **AS-12.** The read path (`get-program.ts`) routes on `identity.legacyPlanId`/`legacyLevelId` — values MIRRORED into `MobileLegacyIdentity` at the P2.1 import — where the live legacy re-reads plan/level per request. `/program` is the first endpoint where a mirror drift yields the WRONG TRAINING CONTENT (a General athlete served the wrong level, or an Individual↔General mis-route) rather than a stale profile field. Inherent to ADR-0043 (we mirror identity precisely so the foreign backend can be deleted), surfaced by the P1.3 review (RF-6). The app does not let an athlete self-change plan/level today (coach-assigned), so no in-app drift path exists; if that ever changes, the mirror needs a refresh path.
  **Closed at P2.2 as a gate, not as an audit.** Two numbers on every report carry it: `mirror diffs` (refreshed rows whose mirrored fields moved against the dump — the plan/level fidelity claim, per row, with the REFRESH section naming the fields) and `RECONCILIATION … violations` (links and identities telling the same story about who a legacy person is). Both are computed on every run, and a violation is a conflict, so a contradicted mapping cannot be written past. What P2.2 deliberately did NOT build is a refresh path for in-app edits — the opposite, in fact: the runbook now forbids post-cutover `--write` re-runs, because `PUT /user` writes profile fields back into the identity and a re-run would overwrite the athlete's own edits.
