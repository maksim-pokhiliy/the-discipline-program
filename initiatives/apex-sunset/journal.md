**The load-bearing discovery — the legacy auth failure surface is 403-empty, NOT 500.** The step was specced (my prompt hypothesis) expecting Spring's default 500 + error JSON on a bad signin. Both the source trace (research agent) and the live harness proved otherwise: EVERY auth failure — wrong password, unknown user, disabled account, bad/expired token, malformed body — returns **403 with a zero-byte body and no content-type**. Mechanism: `AuthConfiguration` sets no `authenticationEntryPoint` → Spring Security 6 defaults to `Http403ForbiddenEntryPoint`; the controller has no `@ControllerAdvice` for `AuthenticationException`; and `SecurityFilter`'s explicit `sendError(401)` for a disabled user never reaches the wire because the servlet error re-dispatch to `/error` re-enters the filter chain, which `anyRequest().authenticated()` denies again → 403, overwriting the 401. This collapses the whole failure surface to one outcome and perfectly explains the sacred "403 drives sign-out" trap: to the app, any auth problem = sign-out. The shim mirrors 403-empty; the golden pins it (incl. the malformed-body and lone-surrogate cases). This is why a live golden is mandatory even with a source trace in hand — the wire behavior is emergent from framework defaults + servlet error re-dispatch, none of which live in the app's own code, and prod drifted from the clone anyway. `harness-facts.md` is the authoritative wire truth, overriding the prompt.

**Design (ratified at the plan gate):**

- **401-not-403 made impossible BY TYPE.** The user services return a `LegacyUserOutcome` union with variants `ok-json | ok-empty | not-found | unauthorized | bad-request` and **no `denied`/403 variant**; `renderLegacyUserOutcome` is an exhaustive `switch` with no `default`. 403 lives only in the bearer wrapper's auth-denial path. A business failure literally cannot compile to 403. (Verified at source by the planner; mutation-proofed by the reviewer.)
- **Anti-IDOR scope-to-self → 404.** All three ops resolve the acting user from the TOKEN's `legacyUserId`; a path/body id ≠ the token's id → 404 (never 403 — a spurious 403 would sign the app out). The app only ever acts on its own id, so the delta is unreachable in production. PUT additionally IGNORES body privilege fields (userRole/isEnabled/trainingLevel/userPlan/username) — anti-escalation.
- **changePassword is an auth write:** verify oldPassword, hash newPassword, and BUMP `tokenVersion` (D-20). Verified safe: `ChangePasswordView.tryChangePassword()` calls `authViewModel.signOut()` on success, so the bump is invisible single-device (the app re-logs in with the new password) and a real multi-device session revocation. Validation = the platform's own `min(12).max(128)` — STRICTER than legacy's 6-char. Owner-flagged delta: existing shorter passwords still LOG IN (login re-checks only MAX, never MIN); only setting a new <12 password is blocked.
- **Schema +2 columns** (`phoneNumber String?`, `dateOfBirth DateTime? @db.Date`) so the athlete's Edit persists phone/DOB losslessly and P2.1 can import them. Date wire = `d.toISOString().slice(0,10)` (yyyy-MM-dd), NEVER `formatCalendarDate` (that renders "Mar 9" and kills the Swift decode).

- **Any request-binding failure → 403-empty, not 400.** A malformed/missing `scheduledDate` or `userId` returns 403 with an empty body — the same Spring Security 6 `/error` re-dispatch swallow as P1.1's auth failures — and 403 drives sign-out. Unreachable via the app (it always sends an Int `userId` + a `yyyy-MM-dd` date), but the golden probes it, so the shim's param guard emits 403 (the DENIED path), NOT its natural 400.
- **The wire `id` is a per-table legacy PK** — `general.id` and `individual.id` both start at 1 and coexist — reused as `MobilePublishedDay.legacyRowId`, so during overlap the shim serves a byte-identical `id`.
- **`dailyProgram` byte-parity was already solved** by `project-day.ts` + its parity test — stored and served as-is, no second shape re-derived.

**Design (D-4 storage shape resolved inside this step; planner-ratified at the plan gate — no new D-number, per the P1.2 precedent):**

- **Snapshot content on `MobilePublishedDay`:** `isRestDay Boolean?` + `dailyProgram Json?` (NULLABLE — the table is already populated by the mobile-publish connector; pre-P1.3 rows carry null content and stay valid; wire id stays `legacyRowId`, no new column). A raw-SQL **XOR CHECK** `("isRestDay" IS NULL OR ("isRestDay" = ("dailyProgram" IS NULL)))` makes the fatalError state unrepresentable at the DB layer. Two link indexes `(channel, legacyLevelId)` + `(channel, legacyUserId)` for the athlete hot read path (the existing uniques all lead with `planId`).
- **The fatalError invariant is unrepresentable at THREE layers:** the projection's return type (`{isRestDay:true} | {isRestDay:false; dailyProgram}`), the DB CHECK, and the serializer (throws `InternalServerError` on `isRestDay:false`+null → 500, never the fatal shape, never 403). Pinned by explicit greppable tests: serializer-throw + DB-CHECK-reject.
- **The rest-day NULL trap:** rest-day `dailyProgram` is stored as `Prisma.DbNull` (SQL NULL), NEVER `Prisma.JsonNull` — `jsonb 'null' IS NULL` is false, so `JsonNull` would make the CHECK reject every rest-day write; `marshalNullableJson` (emits `JsonNull`) deliberately not reused. Pinned by a test.
- **Read serve, everything resolved from the TOKEN (anti-IDOR):** channel by `identity.legacyPlanId` (2→Individual by `legacyUserId`, else General by `legacyLevelId`); the servable snapshot (`isRestDay IS NOT NULL`) ordered `publishedAt DESC, legacyRowId DESC`; scope-to-self (query `userId` ≠ token id → 404). `LegacyProgramOutcome = ok-json | not-found` — a 403-for-a-business-outcome is a compile error (P1.2's no-403-union discipline, extended). Param guard uses `z.string().regex/refine`, NOT `z.coerce` (`Number(null)===0` would turn a missing `userId` into a silent 404 instead of the required 403).
- **Write path:** `recordPublishedDay` stores `{isRestDay, dailyProgram}` from the observed legacy row (faithful to what the athlete actually sees on that key); the legacy push is UNTOUCHED (it feeds the live app until cutover — Sacred; removed at P4.1).
