## Detail on the live ones

**QA-004** — switching a materialized parallel to a non-ladder pattern (Count/Once/EMOM/Interval/Time cap) collapses it to a flat single, silently discarding both authored ladders (no confirm). This is the intended collapse per `D-SCOPE` (non-ladder isn't parallelizable) and is consistent with the codebase's existing wholesale-replace-on-kind-switch (QA-14, which discards a single pattern's body). The defect is the SILENT loss of a whole authored structure. Accepted for step 1 (a confirm dialog would be a new pattern absent elsewhere). Revisit as a UX polish (confirm/undo) if the coach reports losing work; tracked as a product-domain call.

**MARKER-FATE** — `D-CONTAINER-PER-TRACK` leaves `INNER_LADDER_MARKER` in the contract with no authoring path in this flow. It remains valid + readable + seedable. Revisit only if a coach genuinely needs the per-track single-movement rep-scheme case (Block C shape) authored — then it gets its own affordance, NOT folded into the ladder-track flow. **Step-2 note (DR-S2-5):** marker ROWS are not container children, so a hypothetical multi-marker container is NOT structurally parallel and renders label-less ("flat") until that authoring flow exists; the four-projection proof file now pins this stance (the Block C fixture lost its stored arrangement, kept its mirrored marker rows).

**LABEL-COMBINE** — `deriveCompositionLabel` shows one kind; with parallelism now DERIVED (DR-S2-1), the collision is sharper than "parallel OR rounds": BACKLOG-ROUNDS ("N rounds OVER a parallel block") puts `repetition` on the parallel parent, which DEFEATS the predicate's no-repetition qualifier — the parent would read as its repetition, not as parallel. When BACKLOG-ROUNDS lands, the predicate needs an explicit signal and the label must learn to show both kinds. Restated in ADR-0040 §Consequences so the future increment doesn't rediscover it.

## Closed history

**QA-106-RECUR** — CLOSED 2026-06-10 (step 2, DR-S2-7). Inherited from `plan-editor-compose/deferred.md` QA-106: `buildSchemaWithBody` (`schema.mapper.ts:41`) hard-coded `subSchemas: []`, so the write-guard projector only saw depth-2 while real seed data (`block-010`, rounds-over-parallel ladders) is depth-3; the deferred's other option — "assert depth ≤ 2" — was WRONG (would break legit data). Corrected to a step-2 WRITE-path concern on 2026-06-09 (the READ path already recursed via `buildSchemaForest`, fixed in `4a67b6e2`). Closed by fixing the FETCH too, not just the projection: all three production write-guard sites now fetch the block's schemas flat and project via the new full-depth `buildSchemaSubtree`; `buildSchemaWithBody` is DELETED so the cap cannot be silently re-adopted. Depth-3 data survives every write guard.

**MATERIALIZE** — CLOSED 2026-06-10 (step 2, DR-S2-3). `D-FLAT-SINGLE`'s 1st→2nd track restructure raised an id-stability question at two layers. Step 1 resolved the draft layer (DR-3): `materializeParallel` reuses the flat single's draft id for the PARENT (stable top-level ref for the modal's `onUpdateNode`/`onRename`); track 1 gets a fresh child id. Step 2 resolved the server layer trivially: the atomic endpoint mints ALL cuids in one shot inside the transaction — the draft's throwaway UUIDs never reach the wire, so there is no cross-request cuid stability to preserve.

**MATERIALIZE-ATOMICITY** — CLOSED 2026-06-10 (step 2, DR-S2-3). The step-1 persist (DR-2) fired the parent + N track creates as independent `api.schemas.create` calls: a mid-sequence failure left a recoverable partial (parent + k tracks), and a retry re-created the parent (each POST carried its own idempotency key) — accepted degrade-on-peripheral for the UI-first step. Closed by the dedicated `POST …/schemas/parallel`: ONE request → ONE Serializable transaction (mid-failure rolls back the whole tree) under ONE idempotency key (replay returns the cached tree). The failure mode is gone, not mitigated.
