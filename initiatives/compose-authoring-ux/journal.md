## 2026-06-09 — initiative founded; design session, 8 decisions ratified

- **Trigger.** Owner: parallel-ladder authoring is "ОЧЕНЬ сложный флоу", the whole schema-creation UX is unintuitive — "сложность без профита". Diagnosed the real root with him over the session.
- **The reframe (owner's, sharper than mine).** Parallelism is NOT a separate pattern — it's "how many tracks does this ladder have." One ladder = a ladder; N = parallel ladders; **one schema** either way. The coach thinks "a ladder with tracks," not "a container with sub-containers + an arrangement axis." This kills the overloaded create-schema modal (nothing to pick but the pattern tile + its settings).
- **3 verify reports (read-only Explore agents, all 2026-06-09):**
  1. _tracks/interleave consumers_ — `tracks` is always a 1:1 mirror of children; `interleaveOrder` is consumed by nothing but a label. → `D-TRACKS-DERIVED` is safe; ~10 consumer files enumerated for step 1.
  2. _Ladder authoring path_ — the Ladder tile already produces a container `repetition.ladder` + movement rows (the Fran round-counter). Parallel ladders today are stored two ways (nested container tracks vs `INNER_LADDER_MARKER`) → picked container-per-track for the flow (`D-CONTAINER-PER-TRACK`), marker stays a primitive (`D-LADDER` sacred).
  3. _execution inert?_ — composition is INERT; no athlete executor reads it; ADR-0038/0039 confirm. → `D-INERT-FREEDOM`: reshape freely; only the label is live.
- **Owner ratifications.** Only ladders parallelizable (`D-SCOPE`); track = Fran round-counter (`D-TRACK-IS-LADDER`); "2 rounds" = full pass over all tracks then repeat (→ BACKLOG-ROUNDS); UI = "+ another ladder" stepper, don't over-engineer (`D-UI-STEPPER-STACK`, with a current-UI screenshot); 2 steps not 3 (`D-SPLIT`).
- **Decisions ratified:** D-SCOPE, D-TRACK-IS-LADDER, D-TRACKS-DERIVED, D-CONTAINER-PER-TRACK, D-FLAT-SINGLE, D-UI-STEPPER-STACK, D-INERT-FREEDOM, D-SPLIT (all in `decisions.md`).
- **Plan:** 2 steps — (1) contract+model+api reshape, (2) authoring UI. Backlog: rounds-over-parallel, closing tail, non-ladder parallelism.
- **Next:** `/feature` full for step 1.

## 2026-06-09 — Step 1 built & shipped (`/feature` full, branch `feat/compose-ladder-tracks-ui`)

- **Outcome.** The pattern-first "ladder with tracks" authoring flow on draft/mock state. Tiles-first slim create modal; Ladder stepper = track 1; "+ another ladder" stacks a 2nd stepper and materializes the parallel parent in the draft; submit creates parent + N container-ladder tracks via a sequencer; each track card carries the existing "+ Add row". 6 feat/fix commits + this docs close-out; platform suite **961 green**, tsc + lint clean.
- **Gate A — the one real fork surfaced & owner-decided.** Research found the modal authors ONLY a container's axes today (movements/sub-schemas are added post-save on the card, for every pattern). So the walkthrough's "fills its movements … in one flow" had two readings: (A) inline-WYSIWYG movement authoring in the modal (an authoring-model rewrite for all patterns) vs (B) hybrid — stepper-stack in the modal, movements on the post-save track cards (the app's universal grain). Owner chose **B** (DR-1) — consistent with the ratified D-UI-STEPPER-STACK ("just add a button … не усложняем").
- **Persist call (DR-2) — diverged from the prompt's "preferred."** The design agent reasoned, and orchestrator verification confirmed, that writing `arrangement.parallel.tracks` now (the prompt's P3) is Step-2 contamination — that array is exactly what `D-TRACKS-DERIVED` deletes. Verified the board has NO parallel layout treatment at all (`schema-card` renders sub-schemas as a vertical list regardless of arrangement; only `deriveCompositionLabel` reads `arrangement.parallel`), so P3 would buy only a cosmetic label at real cost. Shipped **P2**: structural-only parallel (parent + container-ladder children), the exact tree Step 2 derives `tracks` from.
- **Review ∥ QA caught a CRITICAL static reading missed.** Both agents independently reproduced (driving the real modal) that "+ another ladder" blanked the editor: the materialized parent has no `repetition`, so `activeKind` fell back to "once" and rendered an empty Once instead of the ladder stack — with a hidden bad write on submit (draft still structurally parallel). Root cause = the structural-"kind" trap (parallelism encoded as >1 child, not a field). Fixed via TDD (red-before/green-after): `activeKind = isParallelDraft(draft) ? "ladder" : (draft.repetition?.kind ?? "once")`. The missing Task-9 coverage that let it ship green (REV-W1/QA-002) was written WITH the fix (`create-schema-flow.test.tsx` + modal parallel-submit integration, Must-Test #1-12). Lesson recorded in `decisions.md`.
- **Also hardened in the fix-loop:** stable NodeId track keys (REV-I1/QA-007), container-track index space (QA-006), gated create-mode dead derived-label compute behind edit (REV-I2). QA-004 (silent ladder-discard on kind-switch) accepted for step 1 (matches QA-14); QA-005/MATERIALIZE-ATOMICITY (no rollback on mid-sequence failure) carried to step 2.
- **Decisions ratified:** DR-1..DR-6 (Gate A) → `decisions.md`. **Carry-forwards updated:** MATERIALIZE (draft id-stability resolved; server-cuid → step 2), MATERIALIZE-ATOMICITY (new), QA-004 (new), QA-106-RECUR corrected to step 2 (the "fix in step 1" line was stale — write-path only, zero step-1 UI blast radius).
- **Next:** owner runs the coach-walkthrough on the dev server (the acceptance gate) before merge; then `/feature` for **Step 2** (derive `tracks` on read, re-home `interleaveOrder`, atomic materialization, QA-106 write-path fix, seed reshape).
