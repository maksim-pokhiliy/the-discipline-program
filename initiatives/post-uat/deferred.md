- **🔶 Soft-deleted athletes leak through NESTED relation reads on coach surfaces — CANDIDATE NEXT ITEM, auth-path priority.** OPEN (surfaced 2026-07-27 by the Fix-A investigation). **Mechanism:** the central soft-delete guard is a Prisma client extension (`db/client.ts:119-225`) registered on `$allModels`, and it only intercepts **top-level** operations. A soft-deleted `User` reached through a relation `include`/`where` on some _other_ model is never filtered — the extension simply does not run there. The correct hand-written pattern exists and is used in exactly one place: `coach-athletes/list.ts:26`, `where: { coachId, athlete: { deletedAt: null } }`. Its siblings missed it. **Verified sites:** `coach-dashboard.ts:236-239` (`findMany({ where: { coachId }, include: buildAssignedAthleteInclude(userId) })` — no athlete filter), `coach-action-item.ts:62-65`, `coach-athletes/detail.ts:36-39`. **Highest priority of the group — it is on an authorization path:** `verifyAthleteBelongsToCoach` (`role-guards.ts:64-76`) checks only that the assignment row exists (`findUnique` on `coachAthleteAssignment`, `select: { id: true }`) and never consults `athlete.deletedAt`, so a surviving assignment lets a soft-deleted athlete pass the guard. Not reachable through the admin `deleteUser` today (`applyRoleExit(ATHLETE)` hard-deletes assignments first), so this is latent rather than live — but every path that soft-deletes a user _without_ that lifecycle re-opens it. Receiving schemas here are lax (`z.string()`, not `.email()` — `coach-athletes.schema.ts:18`, `coach-athletes-api.schema.ts:73`, `coach-dashboard-api.schema.ts:36`), so the symptom is a `_deleted_…` email rendered in a coach's roster, not a 500. **This is a property of the soft-delete design, not of post-uat**, so it is recorded where it belongs: `docs/adr/0009-soft-delete-via-prisma-extension.md` § Consequences → "Soft delete is not transitive across relations". Anyone working in `mobile-publish` or `athlete-core` meets it there; this entry is the initiative-side pointer.

- **Soft-delete extension: other gaps found while refuting Fix A.** OPEN, lower priority, same investigation. (a) `prisma.user.deleteMany` (`db/client.ts:260-292`) soft-deletes via raw SQL and bypasses `applyRoleExit` entirely, so assignments / coach profiles / open action items survive — no production caller today (only `db/client.test.ts`), but it is a trap for the next author. (b) The extension does not intercept `upsert` / `update` / `updateMany` / `create`, so those happily operate on soft-deleted rows; `deleteUser` is safe only because it reads through `findUnique` first. (c) `prismaAsCore` (`db/client.ts:310`) is a dead export with zero importers and a type-level escape hatch — delete it. (d) `cleanupRaw`, an **un-extended** `PrismaClient` (`test/helpers.ts:16,254`), leaks out of the test folder into non-test modules under `endpoints/lms/_shared/` — a production import there would get a client that sees soft-deleted rows; candidate for a dependency-cruiser rule. (e) `iamUserAdminApi.updateRole` is unreachable over HTTP — the admin client routes `updateRole` to `PUT /api/admin/users/[id]` (i.e. `updateUser`) and no `/users/[id]/role` route exists, so the method plus its HEAD_COACH-uniqueness check is exercised only by tests; wire a route or delete the method.

- **`resendInvite` is the only user mutation without a service-level actor guard — accepted, not a gap.** CLOSED (by design, 2026-07-27, Fix-A diff review). `updateUser` / `updateRole` / `deleteUser` each open with `requireAdminStrict(actorId)` (`users-admin.ts:93,101,148`); `createUser` (`:49`) and `resendInvite` (`:181`) do not, and rely entirely on the route wrapper. That wrapper is real cover — `withAdminAuth` admits ADMIN + HEAD_COACH and 403s COACH/ATHLETE (`api-routes/src/auth-wrappers.ts:65`) — and the operation is benign by construction: the invite mail goes to the target's own address, an already-onboarded user raises `ConflictError` (`:184`), and `MAX_RESENDS_PER_DAY` caps abuse. D-2.1 leans on this absence as the reason HEAD_COACH keeps Create User and Resend invite, so record it as a **ratified acceptance**: the missing guard is the decision, not an oversight. Consequence to respect: both endpoints are safe **only behind `withAdminAuth`** — a second caller (cron, internal service, a differently-wrapped route) would be unguarded, so anyone adding one owns adding the actor check.

### Wd-1 carry-forwards (2026-07-29, from the profile level-switcher execution)

- **A failed level switch raises the in-card error strip AND a toast — the error signal is doubled.** OPEN (ratified at the Wd-1 plan gate). `useOptimisticMutation` calls `notifyError` unconditionally (`packages/query/src/hooks/use-optimistic-mutation.ts:53`), and a per-call `onError` is additive rather than substitutive in TanStack v5 — so the call site cannot suppress the toast. The ratified design puts the failure message _inside the axis card_, at the point of action, precisely so feedback is not a floating toast; both firing is a compromise, not the design. The cure is an opt-out on the wrapper (an `errorMessage: null` / `notify: false` option, or letting a per-call `onError` claim the notification), which is a diff in `packages/query` — outside the wave's zero-`packages/`-diff boundary. Whoever touches that hook next should take it; every optimistic mutation in the app inherits the same constraint.
- **The profile card chrome is copy-pasted a third time.** OPEN, cleanup. `p / bgcolor: background.paper / 1px solid divider / borderRadius` now appears in `athlete-details-card.tsx:78-83` and in the new `profile-axis-card.tsx` — and the section that used to carry it lost it when the header moved outside the card. A module-level card shell is the right extraction (manifesto: extract on the second instance), but it reaches into two cards this wave had no business editing.
- **The option row and the outcome strip are Wd-2's raw material and are deliberately NOT in `@repo/ui` yet.** OPEN by design. The Level Switch Spec § 6 requires the training-day session sheet to reuse these rows verbatim — same value names, same Current treatment, same Applying flight, same green strip. They were kept inside the platform module (`profile-option-row.tsx`, `profile-axis-outcome-strip.tsx`) rather than promoted early: one call site is not a pattern. Wd-2 is where the second call site arrives, and that is the moment to decide promotion — if it instead copies them, the two homes drift and the spec's "nothing about the selection state may differ between the two" quietly dies.
- **⚠️ Offline mutations PAUSE, they do not fail — the ratified "dev-tools offline" acceptance only holds because of a client-side guard.** OPEN, and the one item worth a decision. `QueryProvider` sets no `mutations.networkMode` (`packages/query/src/providers/query-provider.tsx:16-23`), so query-core's default `"online"` applies: with no connection the retryer does `pause().then(run)` and the promise `mutateAsync` returns **never settles**. The switch would then sit in flight forever — spinner up, group locked, no error strip, no Retry — until connectivity returns (it does self-heal, and a reload silently discards the pick). Wd-1 mitigates in-boundary: `applyPick` refuses to start when `navigator.onLine === false` and reports the ratified failure strip immediately, which makes the owner's acceptance step ("dev-tools offline → the row reverts, the error strip appears with Retry") true. That guard is honest but narrow — `navigator.onLine` is true on a captive portal or a dead-air mobile connection, and those still hang. **Recommendation: add a `networkMode` passthrough to `OptimisticMutationConfig` and set `"always"` for the profile mutation**, so a doomed write fails like a write instead of queueing invisibly. That is a diff in `packages/query` and inherited by every optimistic mutation in the app, which is why this wave did not take it.
- **The radiogroup implements no roving tabindex and no arrow-key navigation — ratified, not an oversight.** CLOSED (by design, 2026-07-29, Wd-1 plan gate). `role="radiogroup"` conventionally promises arrow-key traversal with a single tab stop; here every option row is its own tab stop and Enter/Space activates. The owner ratified the trade-off explicitly: the roles still give the screen reader the state ("checked, 2 of 3"), the rows stay reachable and operable, and hand-rolling the full APG pattern on a group of two-to-four options does not pay for itself. Standing condition attached to that ratification: **arrow-key navigation must not be promised anywhere** — not in a doc, a test name, or a PR body. Revisit only if an athlete on assistive tech actually trips on it; the code reviewer will keep raising it, so this entry is the answer.
- **The applied strip names only the FIRST missing coordinate.** OPEN, cosmetic. `buildMissingCoordinate` returns the first unpicked axis (prototype-faithful — the Claude Design source does `missing[0].name`). With two axes, first-missing and only-missing coincide, which is Denys's current catalog; with three or more the athlete is told about one gap, fixes it, and only then discovers the next. Naming all of them is a copy change, so it belongs to whoever revisits the strip's wording.
- **A stale pick can now be replaced but not cleared.** OPEN by design, 2026-07-29. When a coach removes a value an athlete still holds, the card reads "Not picked" — and the clear control is gated on the catalog-resolved value, so it no longer appears. That was deliberate: the previous cut rendered "Clear the Level pick" directly beside a chip insisting nothing was picked. Consequence: the orphan key stays in `profileSelections` until the athlete picks a valid value (which overwrites it). Harmless for resolution — the server ignores a value that is not in the axis — but a tidier fix would prune orphan keys server-side on axis update.
- **The axes catalog has no error state.** OPEN. `useAthleteProfileAxes` errors leave `data` undefined, and the section renders a spinner for undefined rather than the old "No training classifications yet — your coach defines these", which was a lie while the query was merely in flight. A permanently failed catalog fetch therefore spins forever instead of offering a retry. Same shape as the athlete movement catalog's missing retry (W1 carry-forward above) and worth solving once for both.
- **The athlete's sex is named as a level coordinate but cannot be picked here.** OPEN, small UX seam. The applied strip names the full resolved coordinates including sex, and names "Gender" as missing when it is unset (`buildMissingCoordinate`) — but the control that sets it is the Details card further down the same page, and nothing links the two. A fresh athlete can read "Gender still not picked" with no affordance in view. Wd-2 owns the session-side prompt (`inline-gender-picker` already exists there); the profile-side link is unclaimed.
