## 2026-07-27 (late, +5) — Fix-A: the list-brick was refuted at runtime; the prod-delete freeze is lifted

The rewritten prompt worked as intended — the executor ran the full `/fix` pipeline, and its investigation stage **overturned Finding 1**. The recon had read `users-admin.ts:36` statically, seen no `where: { deletedAt: null }`, and concluded that soft-deleted rows leak into the admin list where the suffixed email fails `adminUserListItemSchema`'s strict `.email()` → permanent 500. Every line reference in that recon is exact; the conclusion is not, because this repo filters soft-deletes **centrally** — `db/client.ts:7-16` puts `"User"` in `SOFT_DELETE_MODELS` and the `$extends` block (`:119-225`) injects `deletedAt: null` into top-level `findMany`/`findFirst`/`count`/`aggregate`/`groupBy` and null-filters `findUnique`. A bare call site is the _expected_ shape here. The refutation was not taken on the agent's word: the guard test was written first, confirmed green on `main`, then `"User"` was temporarily removed from `SOFT_DELETE_MODELS` and the same test went red with exactly the predicted `validation: 'email'` / `"Invalid email"` at `users[N].email` — proving both that the mechanism is real and that the guard has teeth, before the mutation was reverted. So the predicted 500 sits one config line away from being real, which is the whole argument for keeping the test.

Consequences ratified at Gate A: **Fix A ships as regression guards only** (list re-read + schema parse, by-id 404, dashboard counts/activity — zero production diff), and **the standing "no user deletion in the prod admin" freeze is lifted** — it had been costing real operational capability for a defect that does not exist. Also accepted at the gate: standing up vitest infrastructure for `apps/admin`, which had **zero** tests, no config, no runner and no testing-library deps — the per-role UI test could not otherwise exist.

Grouped rows, which were structurally incapable of interaction (the group renderer destructured the load line and threw the prompt away), now render the identical cell component as plain rows. The applied moment holds its "Applying…" flight across both the write and the session refetch before closing onto a pulse and a receipt — there is no optimistic path for session numbers, so firing earlier would have highlighted the numbers the athlete already saw. PU-04's wedge closed twice over (see D-21). The Wd-1 option row, strip and coordinate builders moved to `@app/lib/level-switch` with the flight core extracted; the profile page's 127 tests passed on import paths alone, with one four-line exception where a ratified constant rename touched a test body — recorded rather than aliased away.

**Gate A** went to an external tech-lead review and came back approved with three corrections, all folded in before code: the prod audit must import the guard's own classifier rather than restate it; a non-zero audit blocks the merge but authorises no write; and the unpicked single-axis label renders full coordinate values, overriding the plan (D-19.1).

**The production audit passed — and confirmed the hypothesis literally.** `REJECTED = 0`, so the merge gate cleared. It also found two free-text `GENDER`/`Gender` keys on one athlete, valued `"Male"` while her typed column reads `FEMALE` — the pre-rekey artefacts the historical backfill helper existed for. Gender keys in that column were not a theory.

**Then the `max` review refuted a ratified decision, and the refutation is the most valuable thing this wave produced.** 55 agents, 15 confirmed defects, three of them silent data loss on a live athlete surface. The worst was mine: the guard's _pruning_ half shipped on the RFC's claim that catalogue-orphaned and catalogue-stale keys are "already inert at read time". They are not. `resolve-load.ts:25-33` resolves a per-profile weight against the **plan's own stored axis snapshot**, never against the live catalogue — so a coach renaming a value leaves published plans still offering the old one, the athlete picks it, and the guard deletes the pick behind a 200 and a green receipt, taking the rest of her selections with it. Owner ratified the correction the same day: rejection stays, pruning goes, and the deferred item asking for exactly that pruning closes as **must not be done** (D-20).

Two more of the same shape followed. The level patch built a wholesale replace on an empty base whenever the profile query was still in flight — the sheet is tappable in that window by construction — erasing every pick on axes the tapped row does not use. And D-21's idempotency fix would have wedged production while its tests stayed green, because the fixture froze `recordedAt` while both call sites stamp it per press; an agent traced the precondition into a file it did not own and reported it instead of declaring done.

**The lesson, sealed:** a validation or repair guard on a write path is ratified only after tracing **every reader of that column across time** — each published plan snapshot is a reader that outlives catalogue edits. "Inert at read time" is a runtime claim and needs runtime proof. The owner recorded it as the second flavour of the read-surface-trace rule; the same law that Fix-A taught, now covering writes. Twice in one wave the same epistemic error appeared: a claim verified against one slice of the input class and generalised to the whole of it. The prod audit itself was an instance — it proved safety for the rejection branch and never exercised the prune branch at all, while the two rows it found were inert for a reason (free text can never match a cuid axis id) that does not extend to the class the rule was written over.

## 2026-07-30 — Wd-2 fix round on the external review of PR #357

Nine items came back on the PR, and the useful thing about them is that none were about the chip. They were about what the chip _claims_. The receipt counted every weight the applied axis governs and called them all updated — so re-stating the level already in force produced "Scaled · Female applied · 4 weights updated" over four numbers that never moved. The count now comes from a delta: `kgForCoordinates` resolves each row's own grid under the drafted coordinates and only the rows whose number actually changes get counted and pulsed. The sheet's scope line keeps the wider set on purpose — "applies to N weights" is a statement about reach, and that one was already honest.

Two more were the same species of lie. A failed refetch fired the full receipt over stale numbers, which is the exact perception failure D-19 stretched the flight across two round trips to prevent; it now says the screen needs a refresh. And the apply flight was a hook-level boolean, so closing the sheet mid-write and tapping another chip rendered a sheet with every option locked and no explanation — the flag is now bound to the sheet instance, and a second sheet says "Applying your last pick…" on a disabled CTA rather than dying silently. Level applies stay serialised (one column, read-modify-write); max saves do not need to be (append-only), so they are not.

D-22 is the one that mattered most to get on paper. The UTC → viewer-local flip was right — `recordedAt` is an instant, and a 01:00 Kyiv max is a Tuesday max — but it shipped as a renamed test and nothing else, on a screen that was already live. It now owns a decision entry, the formatters carry `Local` in their names beside `@repo/shared`'s `formatCalendarDate`, and the PR states the cost instead of claiming clean backwards compatibility: records saved between midnight and 03:00 Kyiv render one day later than the day picked. The modelling debt underneath — a calendar day stored as an instant, with the time-of-day pure `now()` noise — goes to Wd-3, which is the wave that edits dates anyway.

**The lesson:** every count, every green toast and every disabled control is a claim, and the review found four places where the claim was wider than the fact. Cheap to state, cheap to test — each of the four is now pinned by a test that was red before the fix.
