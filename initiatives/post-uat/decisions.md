  - **D-2.1 — Fix A refuted; prod user-delete freeze lifted.** RATIFIED 2026-07-27 (Gate A, Fix-A executor run) — SUPERSEDES the "list-brick — now URGENT" premise in D-2 above. The list-brick that made Fix A urgent **does not exist**. Soft-delete filtering is central (`db/client.ts` `SOFT_DELETE_MODELS` + the `$extends` block), confirmed at runtime and pinned by a mutation test; details in `triage.md` § PU-06 "Investigation outcome". Consequences: Fix A re-scoped to regression guards only (no production diff), and the standing **"no user deletion in the prod admin" freeze is LIFTED**. Fix A′ is confirmed and ships with one scope correction: the UI hides exactly what 403s — Delete, the role-change interaction, the edit-form Save — while **Create User and Resend invite stay visible and working**, because `createUser` (`users-admin.ts:49`) and `resendInvite` (`:181`) carry no actor guard. The guards themselves remain untouched, as ratified above.

  - **D-2.2 — The honest-UI rule extends to the IDENTITY axis: an ADMIN's own row loses Delete and the role chip.** RATIFIED 2026-07-27 (owner, Fix-A diff review) — a deliberate scope expansion over D-2.1's "ADMIN sessions stay exactly as they are". The diff review found the same dead-affordance class this fix removes for HEAD_COACH, one axis over: an ADMIN sees Delete and a clickable role chip **on their own row**, and the server rejects both unconditionally — `Cannot delete yourself` (`users-admin.ts:152`) and `Cannot demote yourself from admin` (`:110`, which fires for every reachable change, since any role move away from ADMIN is a demotion). Owner's ruling: **"ADMIN sessions unchanged" meant "do not cut capability", not "keep dead buttons"** — the thesis of this change is that the UI does not lie, and that applies by identity as much as by role. Scope, precisely: in the users LIST, `Delete` and the role-chip interaction are hidden when `user.id === session.user.id`; the row's Edit link is untouched. The **detail form of one's own record is NOT touched** — Save there is legitimate, because `updateUser` accepts name/timezone edits on yourself. Mechanism: `useCurrentUserId` joins `useCurrentUserRole` in `@repo/auth/client`.

- **D-6 — 1RM movement-picker scope (PU-01).** **RATIFIED 2026-07-27 = (a)** — athletes get the read-only movement catalog (owner: «пусть ставит что хочет»). Born from the owner's design-check 27.07: "там только движения, которые тренер пометил как бенчмарк — или нет?"). Verified answer: **no** — the list is scoped to the athlete's OWN `OneRMRecord` rows (coach influence is indirect: `% of 1RM` prompts and LOAD-benchmark side-effect appends create records); a fresh athlete has a permanently empty picker and can never proactively log a first 1RM from Records.   - **D-6.1 — the CONCRETE filter belongs to the CATALOG QUERY only; own-record movements are never nature-filtered.** RATIFIED 2026-07-28 (owner, W1 plan gate) — an addendum, because D-6's acceptance line "PLACEHOLDER/REST never appear" is **unsatisfiable as literally written** once the union exists. The picker's option list is the union of the catalog and the athlete's own record movements, and nothing in the schema stops an `OneRMRecord` from pointing at a `PLACEHOLDER`-nature exercise (a coach can set a `% of 1RM` row on one). Nature-filtering the union breaks the preset path: `record-card.tsx` fires `onUpdateOneRm(exerciseId)` → the form resolves it via `movements.find(...) ?? null` → a miss leaves `activeMovement === null` → **Save is permanently disabled with no error**, turning "I can't add a new movement" into "I can't update an existing one" — strictly worse. **Restated acceptance:** _the catalog never offers PLACEHOLDER/REST; movements the athlete has already logged stay pickable regardless of nature._ Pinned by a test the owner required at the gate (an athlete with a record on a non-CONCRETE movement opens the preset → the movement is in the options → the submitted `exerciseId` is theirs), so the regression cannot return silently.

- **D-8 — The athlete gets history-hygiene rights on his OWN 1RM records (supersedes the D-5 "not history editing" clause).** RATIFIED 2026-07-28 (owner, at the Wd corpus read): a mistyped-then-corrected max leaves a garbage record sitting in the history forever — not acceptable. The exact operation set — edit / delete permanently / exclude from stats, any subset — and its look & behavior are questions for the Wd design round. Tech-lead recommendation into that round: **edit + delete only** — "exclude from stats" is indistinguishable from delete in this product (stats = the history list + latest-wins resolution; there is no aggregate analytics an excluded row would meaningfully stay out of) and costs a permanent flag in the model plus a filter in every reader (resolution, history, the PU-01 catalog union). Invariants that survive any design outcome: records stay athlete-owned; latest-wins resolution stands — editing or deleting the LATEST record retroactively moves the current working weight, and deleting the last record of a movement returns its percentage rows to the "enter your max" prompt (the design must surface this consequence, not hide it); appending stays the natural flow for new maxes. Same owner round: the "don't slam the popover" polish sketch from the PU-03 fix sketch is DROPPED («это не нужно»), and the PROFILE-page level switcher joins the Wd scope — plain Buttons-as-toggle is a semantic misuse (the only "selected" signal is a variant change, which the athlete did not read; MUI has dedicated selection primitives — ToggleButtonGroup / selectable Chip / Radio — and the "applied" feedback moment is the design round's call).
