**Sequencing rationale.** data → UX → metrics mirrors the dependency chain: the UX needs the data shape, the metrics need logged data. Block 1 is ONE coarse wave (the data model is one connected design — `Performed*`, records, result-types, resolver, publish-snapshot — splitting it atomically would just add merge bureaucracy). The benchmark/template CATALOG is a separate wave (coach-side, fusion-gated), off the athlete-logging critical path.

**Open design details deferred to step 0** (so they aren't silently decided early): the `Performed*` redesign shape (how each of the 6 kinds is logged); the result-type discriminated shape; the publish snapshot model (working vs published); the date-thread field on enrollment (reuse `boardedAt` + a hide-past flag, or a new field); records/PR derivation (best-of query vs stored); the resolver's shape (byProfile cell-pick by athlete profile + %-of-1RM lookup).
