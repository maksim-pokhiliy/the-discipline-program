## Block-2 screen-2 in-schema benchmark-logging re-home carry-forwards (2026-06-19)

- **`performed-session` completion IDOR guard Forbidden → NotFound re-align (D9) — focused cleanup.** The new result endpoint's guard `assertSessionReachableByAthlete` throws `NotFoundError` (matching the read guard `session-detail.ts` + the project IDOR→NotFound invariant). Disposition: a documented inconsistency (new endpoint NotFound, completion Forbidden); re-align the completion guard to `NotFoundError` (+ update the QA-004 test) in a focused cleanup so all athlete read/write guards leak existence the same way.
- **QA-008 — multi-movement `load` benchmark (e.g. CrossFit Total): which exercise gets the 1RM?** A `load` result writes its `OneRMRecord` to the FIRST `SchemaRow` by `order` — a "find 1RM" benchmark is single-movement by convention (matches how `firstMovement`/`benchmarkTitle` pick the first row). A multi-lift "Total" (snatch+clean&jerk, or squat+bench+deadlift) would silently write the 1RM to only the first lift. Owner ruling at the live test: **"Total пока не в планах"** — accepted as a known convention for now. Disposition: revisit if a real multi-movement `load` benchmark appears (athlete-POV) — either reject it at validation, or write a result-without-1RM (history only) for the multi-lift case, or model per-movement loads. Not built until a real plan needs it.
- **QA-009 — no `Idempotency-Key` on the result write — optional hardening.** The new `POST sessions/[sessionId]/result` carries no idempotency key, so a retried/double-fired request appends a duplicate history row. Append-history tolerates this (a stray duplicate attempt is harmless trend noise, never an overwrite), and the codebase is keyless on these athlete write endpoints today (the `performed-session` create + `one-rm-records` create are equally keyless). The Idempotency-Key infra exists (ADR-0036). Disposition: optional hardening — add a client-generated key + server dedup if duplicate-row noise ever bites; low priority on an append model.
- **`responseSchema`-parse adoption repo-wide — cleanup.** The api-client has a dormant `responseSchema` parse mechanism that is unused repo-wide. Because of that, `completedAt` is currently coerced to `Date` ad-hoc at the `athlete-session-view` api-client boundary (`lib/api/endpoints/athlete-session-view.ts` — an owner-driven live-test fix: the JSON response delivers `completedAt` as a string, not a `Date`). Disposition: adopt `responseSchema` parsing repo-wide so every client response is validated + date-coerced at the boundary by its contract schema (drops the ad-hoc coercion). A repo-wide api-client cleanup, not this slice.
- **OQ-C — drop `createPerformedSessionSchema.results` once nothing sends it.** D11 kept `results: z.array(...).optional()` + its duplicate-`plannedSchemaId` superRefine on the completion request schema (no contract break — the client simply stops sending it; the server stops reading it). Disposition: a later focused cleanup MAY drop `results` from `createPerformedSessionSchema` entirely once confirmed nothing sends it (touches the schema + the `performed-session-api.schema.test.ts` dup-check cases — deferred this slice as not worth the churn).
